# Accepted limitations

Known behaviours that were accepted on purpose or are not worth fixing in Stage 1, each tagged with its milestone. Reference only: read it when you touch the area, not at session start. Add a line when you accept a limitation.

- The grace period trusts the client's server-synced clock: a save can claim any `clientTs` up to the deadline and still be taken within the grace (M18).
- If the server is down past a student's deadline plus grace, the first watcher tick afterwards finalizes them at once; saves they could not send in that time are lost (M18).
- IPv6 to the teacher is not permitted by the internet filters (IPv4 literals only); a teacher reachable only over IPv6 would be blocked. LAN labs use IPv4 (M21a).
- A student who is offline (no WS) keeps the internet block until the lease runs out or the app lifts it; the dashboard counts only connected PCs in "applied on N of M" (M21b).
- A program that is not the real service can take the agent's pipe name while the service is down; that only blocks the student who did it, because the app never trusts a pipe whose SCM pid check fails (M21).
- The session token is encrypted with the Windows user's DPAPI key, which protects against a copied file, not against the student themself; the token only gives the student their own exam (M17).
- A student can redefine `prompt` or remove the PSReadLine handler in the exam terminal: that line is still reported, later lines are then only in the transcript. Typing into the shell's own `[Console]` (for example `Read-Host`) appears only in the transcript (M15b). The terminal is an in-app channel that focus monitoring cannot see (requirements §11).
- The terminal switch is exam-wide; per-student toggles are Stage 2 (M15b). `terminal_closed` from a shell killed at app quit may not be sent before the app exits.
- A memory-limit hit is reported even if the program caught the failed allocation (intended). A JS out-of-memory run prints V8's long stack to stderr (not trimmed). C output uses CRLF.
- Run flags can reach gcc options such as `-wrapper` or `@file`; no wider than the terminal the student already has, and the Job Object still limits them. A flag that stops before linking (`-c`, `-E`) ends as a failed run (M15c).
- A program waiting on input for the 10 min wall time is killed as `time_limit` (M15c). The console is bound to the run panel: switching question or language remounts it and replays the last output; output of a run still going has no console to land in. A run started with a hidden console uses 80×24.
- `graphics.h` (WinBGIm) is not in the MSYS2 ucrt64 repo; students download it into `workspace\include|lib` (needs internet) and pass `-lbgi -lgdi32 -lcomdlg32 -luuid -loleaut32 -lole32` (M15c).
- pacman runs with `--noscriptlet` (packages that need install scripts may be incomplete), only `[ucrt64]` is configured, and `npm i -g` is not supported (local installs only) (M15a, M15d). `pip --target` puts everything in one folder: a second install at another version needs `--upgrade`, uninstall only works through `python -m pip`, and a package with no Windows wheel needs a compiler that is not wired in (M15d).
- Files panel: the 200 MB disk limit is checked only when the panel saves or creates, so a program can write past it and the panel then refuses saves; it reads the folder when shown and when a run ends (use Refresh for files made in the terminal); an edit made in the last 0.6 s before Run may be written after the program has read the old file; one `main.c` only (no multi-file builds), a relative `require('./x')` from `main.js` and ESM `import` from the workspace do not resolve (M15c, M15e).
- Teacher-provided files: locked once hosting starts (stop hosting, edit, host again); students who joined earlier get the new list at their next `welcome` and already-copied files are not replaced; they count toward the student's 200 MB quota; a file the antivirus blocks shows as a failed download; the download has a 20 s idle timeout per read and no overall limit (M15f).
- Autosave: while the link is down saves pile up in memory (cap 500, a later save of the same buffer supersedes the older); a failed `answer:save` IPC makes the renderer forget that buffer so the next tick resends it; a half-open socket is noticed only by the 15 s idle drop (M16).
- Every autosave is a full copy of the buffer (up to 128 K characters), so a long exam keeps many versions; 200 students × a save every 10 s of a 4 KB answer is about 80 KB/s into SQLite (M16).
- The transcript client cap (about 1 MB per app run) restarts from zero after an app restart; the server cap still applies (M17).
- A relaunch while the server is unreachable shows the lobby ("Connection lost. Trying again…"), not the exam, because the exam state is only known from the server; the work is safe in the queue (M17).
- `network_lost` needs the exam `running` and the student `active` or `locked`; a student who disconnects after submitting stays quiet (M17). "Leave this exam" is offered only while the link is `reconnecting` or `failed` (M17).
- The window stays locked while the exam is `running` and the student is working, as intended, if hosting stops or the teacher server dies. Windows shutdown/log-off fires `before-quit`, which is cancelled while locked; Windows may still force it (M13).
- `pnpm fetch-toolchains` must be run once per checkout (about 280 MB download, about 1 GB unpacked, gitignored) and `cargo build -p eg-runner` before `pnpm dev:student`. The Dev-C++ gcc 4.9 on some PCs does not support `-std=c++17`, so `EG_MINGW_DIR` must not point at it (M15).
- Window programs and processes under `eg-runner` (GLUT, tkinter, matplotlib) run in the student app's job. M22 counts a foreground window of any program the app started as inside (so no focus-loss event); M23's `app_launched` treats them as expected too (descendants of the exam app's process).
- Outside time (M22): the roster total grows only when the student comes back (`focus_returned`), so a stretch still in progress is not counted yet, and one that never ends (the exam ends first) is not counted at all. Alt-Tab, the Start menu and similar shell windows are foreground changes and show as short `focus_lost` / `focus_returned` pairs for `explorer.exe`; M31's classifier is where to filter them.
- Evidence buffer (M24): at most 500 unacked entries (the oldest go first); if `buffer\` cannot be opened the service falls back to memory (100 entries, lost on a restart). Undelivered evidence of a previous student on the same PC is deleted when the next student's monitoring starts.
- Relaunch (M24): monitoring is not remembered across an agent restart or a reboot, so after a reboot nothing relaunches the app until the student opens it (the buffered evidence is then delivered). In dev, a relaunched `electron-vite dev` app only renders if the Vite dev server is still running; try the relaunch with a built app (`pnpm --filter @examguard/desktop build`, then `electron out/main/index.js --profile student`).
- Tamper lock (M24): the lock is the app's own overlay, so a modified app could skip it; the server still records `agent_lost` and the student's `agentOk`. After a teacher unlock with the agent still down there is no new lock until the link comes back and is lost again. A student whose app lost the agent while also offline is locked on the server only once the event arrives.
- Process watcher (M23): it polls once a second, so a program that starts and ends within a second is missed; the pid list is compared by id only. Under `eg-agent --console` (not elevated) the token of an elevated process cannot be read, so such a process counts as the user's and some extra system processes show up in dev; the installed service reads every token. The ignore list of Windows background hosts is fixed in `procwatch.rs` until M31's classifier.
- Paste guard (M25): the remembered copies live in the renderer, so after an app relaunch (or a reload) text copied before it no longer pastes, and the clipboard is cleared again anyway. Pasting into other programs is not watched (the agent reports switching to them). The guard is the app's own code, so a modified app could skip it. Dropped files are not checked; only dropped text is. Text copied from the exam into another program and copied back is allowed if unchanged.
- Screens and secure desktop (M26): `SM_CMONITORS` counts screens that are part of the desktop, so a mirrored (duplicate) display or a TV set to "show only on 2" while the laptop panel is off counts as one; a screen change is seen within about 1 s and only while monitoring runs. Ctrl+Alt+Del, Win+L and a UAC prompt all use the `Winlogon` desktop, so they look the same (`secure_desktop`), at most one per 5 s, without a screenshot (a capture cannot see that desktop). Task Manager started before the exam only shows in `processes_at_start`.
- Large insertion (M27): a typing tool that waits 25 ms or more between keys is not flagged (normal auto-repeat is about 33 ms); the exam terminal is not watched; Monaco edits at several places at once (rename, multi-cursor) and a long copy of text already in the editor count as the editor's own; within 500 ms of an allowed paste, a burst up to twice its size is not counted.
- Classification (M31): the short/long outside limits (10 s / 60 s) and the risk points are constants until Settings (M43); the risk score only grows; shots while away are timed on the student PC's clock; events stored before M31 keep their old severity and add no risk; exams created before M31 have an empty high-severity list unless the teacher fills it.
- Thumbnails (M29, M33): only the primary screen is captured (a second screen shows in the roster's screen count, not in the grid); a capture on the secure desktop gives no picture, so the tile keeps the last one and dims it after 15 s; a teacher socket more than 2 MB behind skips frames (all 200 on one page can skip a student's first frame, which then arrives one interval later); the grid's order can move a student to another page as the risk score changes.
- Teacher actions (M35): unshown messages are kept in server memory only (a server restart loses them; the audit log keeps the text), and the app acks a message when it arrives, so an app that crashes before the student closes the popup does not show it again. Extra time can only be added, not taken back. Locking and ending need a running exam; the confirmations are the browser's `confirm` dialog.
- Installer (M45–M46): unsigned and with the default Electron icon (no ExamGuard icon yet); the "delete data" uninstall choice reaches only the Windows user who runs the uninstaller (other users' `%APPDATA%\ExamGuard`, students' `%LOCALAPPDATA%\ExamGuard\run` workspaces stay); an install folder an administrator picks outside Program Files is trusted as it is (the agent's program file and `AppPath` live there); the firewall rules cover the Domain and Private profiles only.
- Load and hardening (M47, M49): the load numbers come from a plain Node server process on the dev PC with the sim on the same PC (no Electron, no real network); the laptop run is manual. There is no per-token WS rate limit: a signed-in student's app could flood saves or events (frames are capped at 512 KB, each is validated, and the student is known), because a legitimate offline replay can be hundreds of frames at once. `minimatch` (ESLint, electron-builder) has a ReDoS advisory; it only runs at build time.

## Small follow-ups without an owner (moved from progress.md, 2026-11-03)
- tell the teacher which students' exam-file download failed (an app event in the hosting panel); show the exam from the first second after a relaunch by caching the last `SessionState` in the session file; copy/print/save for the receipt (the hash is shown in full); a "hosting stopped" screen for students whose socket drops because the teacher stopped hosting (they see "reconnecting" and retry); show offline PCs in "applied on N of M" and decide how a PC that lost its link is released from the internet block; a "switch exam without an uninstall" path for a student whose link is `connected` to the wrong exam (Settings); `confirm` does not check that the exam is still hosting; the join rate limiter is in memory and keyed by the socket IP; `resume.lastServerSeq` stays 0 (M35 re-sends messages after each welcome instead); the teacher login screen does not show the "server restarted" banner after a restart; exams list and class-list students view are not paginated; class lists cannot be renamed or edited per student, and re-import into an existing list is not built; the question form has no markdown preview or "unsaved changes" prompt; the answer store is not cleared between exams in one app run (question ids are unique, so harmless); the server's WS `notice` message from protocol §3 is not built.
