# Architecture

Scope: how the pieces fit together. Tables are in `data-model.md`, message shapes in `protocol.md`, build order in `milestones.md`. Behaviour rules (what counts as an event, severities, limits) come from `requirements.md`. This doc only says *how* they're implemented.

## 1. Processes

### Teacher PC (install type = Teacher; no agent)
| Process | Role |
|---|---|
| Electron main (`apps/desktop/src/main`) | Window, teacher login gate, `safeStorage` (API key, secrets), power-save blocker while hosting, starts/restarts the server |
| Renderer (teacher UI) | React app. Talks to the server over **loopback HTTP/WS** (`127.0.0.1:47821`) with a teacher token handed over by preload |
| Server (`apps/server`, Electron `utilityProcess`) | Fastify. Two listeners: student HTTPS/WSS `0.0.0.0:47820` (on only while hosting) and teacher loopback `127.0.0.1:47821` (always on). Owns SQLite, mDNS advertising, the exam timer, event classification, risk score, thumbnail fan-out, WebRTC signaling and the grading pipeline |

Main restarts the server on exit with backoff (1 s, 2 s, 5 s, then every 10 s). Each restart is logged and shown as a banner. If main itself crashes, students reconnect after the teacher relaunches the app (§6).

### Student PC (install type = Student; locked to Student mode)
| Process | Runs as | Role |
|---|---|---|
| `eg-agent` service | LocalSystem, session 0 | Owns the app pipe, process watcher, helper lifecycle, encrypted evidence buffer, heartbeat |
| `eg-agent --helper` | SYSTEM token in the active console session | Foreground/title hooks, screenshots, monitor count, secure-desktop detection, relaunching the app |
| Electron main | Student user | Exam window, pipe client, code runner, offline queue, screen capture for thumbnails and WebRTC, clipboard control |
| Renderer (student UI) | Student user | Exam UI and Monaco. No Node access |
| `eg-runner.exe` + student program | Student user | Job Object sandbox for one code run |

## 2. Networking
- **Student → server:** HTTPS for join and bootstrap, then one WSS connection per student (`/ws`). It carries JSON frames, plus binary frames for thumbnails and screenshots. Port 47820 by default, configurable in Settings.
- **Discovery:** the server advertises `_examguard._tcp` over mDNS (bonjour-service) while hosting. TXT record: `v` (protocol), `exam` (title), `fp` (SHA-256 cert fingerprint, base64url). The student app lists every host it finds. Manual entry of `IP[:port]` is always available (teacher on Wi-Fi, different subnets).
- **TLS:** the teacher app generates one ECDSA P-256 self-signed cert per installation (`certs/`) and regenerates it on request. The student app pins the fingerprint:
  - via mDNS: the `fp` from TXT must match the presented cert
  - via manual IP: trust on first use for this exam. The student screen shows a **4-character code** (first 20 bits of the fingerprint, Crockford base32) next to the PIN field, and the teacher's hosting screen shows the same code. Invigilators compare them by eye.
  - the pinned fingerprint is stored with the student's session, so a reconnect to a different cert is refused.
- **Teacher UI → server:** loopback only, plain HTTP. The token is random per app launch, passed from main to the utilityProcess and to preload. Never bound to the LAN. HTTP calls send it in the `X-Teacher-Token` header; the WebSocket (`/ws`) takes it as `?token=` because a browser WebSocket cannot set headers.
- **WebRTC:** peer-to-peer on the LAN using host candidates only (no STUN/TURN, no internet). Signaling is relayed over the existing WS connections.
- **Firewall:** the installer adds program-based inbound rules (TCP + UDP) for `ExamGuard.exe` on Teacher installs only. Student PCs make outbound connections only. ICE checks from the student side open the stateful path. During an exam the agent may add temporary internet-off WFP filters that always allow the teacher PC (§3).
- **Limits:** WS max frame 512 KB (screenshots are chunked if larger). Per-token rate limits on saves/events, and a per-IP limit on `/join` that counts failed tries only (5 wrong PINs or unknown IDs per minute, then 429 `rate_limited` with `retryAfterSec`), so a lab behind one address is not throttled. Every inbound frame passes `safeParse` against `packages/shared`.

## 3. Monitoring agent (Rust)

**Crates:** `windows` (Win32), `windows-service`, `tokio`, `serde`/`serde_json`, `tracing`, `jpeg-encoder`, `aes-gcm` (buffer encryption).

**Service (session 0)**
- Starts at boot (auto-start, recovery = restart). It can't be stopped by a standard user, because the default service ACL only lets admins stop or change it.
- Watches `WTS` session notifications. When a user logs on it launches the helper in that session: `DuplicateTokenEx(own token)` → `SetTokenInformation(TokenSessionId)` → `CreateProcessAsUserW` on `winsta0\default`. The helper runs as SYSTEM, so the student can't kill it. If it exits, the service restarts it within 1 s and logs `helper_restarted`.
- **Process watcher:** polls a ToolHelp snapshot every 1 s, diffs it, and reports new processes owned by the interactive user (exe name, path, PID, parent). Also reports the full list at exam start.
- **Pipe server (M21):** `\\.\pipe\examguard-agent`, created with `FILE_FLAG_FIRST_PIPE_INSTANCE`, `PIPE_REJECT_REMOTE_CLIENTS` and three instances created up front (`max_instances` = 3, each worker keeps its instance and only disconnects and listens again), so no other process can ever create an instance and a client can only reach the service. DACL: SYSTEM full control, the interactive user `FILE_GENERIC_READ | FILE_GENERIC_WRITE` (`0x12019f`; Node/libuv asks for exactly that and falls back to a one-way pipe with less, and it includes the right to create an instance, which the saturated instance count makes harmless) (`pipe_security.rs`). **The service verifies the app:** on connect it calls `GetNamedPipeClientProcessId` and `QueryFullProcessImageNameW` and compares the result (case-insensitive) with `HKLM\SOFTWARE\ExamGuard\AppPath`, a value only an administrator can write (the installer in M45; the dev install scripts write Electron). Anything else is disconnected before it can send a byte, and logged (`rejected pipe peer`). With no value registered nobody is allowed. Frames are a 4-byte little-endian length followed by UTF-8 JSON (shapes in `protocol.md` §4).
- **The app verifies the service** without native code, because Node cannot call `GetNamedPipeServerProcessId`: the agent's `hello` carries its `pid`, and the app accepts it only if `sc queryex ExamGuardAgent` reports the same pid and `sc qc` shows the installed `%ProgramFiles%\ExamGuard\agent\eg-agent.exe` (a folder a standard user cannot write to). Together with the three saturated instances and the access list, a user process can neither create the pipe nor answer for the service. (Decision 2026-10-23.)
- **Helper link (M21):** a second pipe `\\.\pipe\examguard-helper` with one instance, SYSTEM only (the helper runs as SYSTEM; under `--console` the owner may connect too). The helper connects and reconnects every 0.5 s; the service sends `check` and the helper answers with a test capture result and the monitor count. The system check is the app's `system.check` answered from that: helper connected, capture not black, at least one monitor.
- **Evidence buffer:** while monitoring is active, every event and screenshot is appended to `%ProgramData%\ExamGuard\buffer\<examId>\`, encrypted with AES-GCM using a key that only SYSTEM can read. Entries are removed only after the app confirms the server stored them (`evidence.ack`). This is how evidence survives an app kill or reboot (decision: relay through the app only, no direct agent → server link).

**Helper (user session, SYSTEM token)**
- `SetWinEventHook(EVENT_SYSTEM_FOREGROUND)` for focus changes, and `EVENT_OBJECT_NAMECHANGE` filtered to the foreground hwnd for title changes. It resolves exe name, PID and window title.
- **Outside time:** "outside" = the foreground window doesn't belong to `ExamGuard.exe`. It tracks the start and end of each outside interval and reports them with durations. Totals are computed on the server.
- **Screenshot policy** (while outside): capture at the switch, on a title change, and every 20 s. Throttled to 1 per 5 s. Full virtual screen (all monitors), downscaled to ≤1600 px wide, JPEG quality 60. Capture uses GDI `BitBlt` from the screen DC, with DXGI Desktop Duplication as a later optimisation if BitBlt turns out slow or black (the M19 spike decides).
- **Monitors:** `EnumDisplayMonitors` at join, at start, and on `WM_DISPLAYCHANGE`.
- **Secure desktop / Ctrl+Alt+Del:** polls `OpenInputDesktop` + `GetUserObjectInformation(UOI_NAME)` every 500 ms. A name other than `Default` means the secure desktop is up. Task Manager is caught by the process watcher (`taskmgr.exe`).
- **App relaunch:** if monitoring is active and no `ExamGuard.exe` is connected to the pipe for 3 s, it launches the app in the session with the *user's* token (`WTSQueryUserToken`) and logs `app_relaunched`.

**Heartbeat and tamper lock**
- The service sends `heartbeat` every 2 s and the app replies. If the app misses 3 heartbeats (6 s), or the pipe breaks or fails verification, the app locks its own UI, sends `agent_lost` (critical) to the server, and the server marks the student Locked. Only the teacher can unlock.
- Join is refused unless the pipe is verified and `systemCheck` passes (helper alive and a test capture is non-black). The app runs a fresh check before each `/join` and refuses locally; the server refuses a join whose `agent` block is not healthy (403 `agent_required`). After joining the app sends `agent.status` over the WS after each welcome and on every change, which drives the teacher roster's `agentOk`. **M21 only reports the link:** the lock overlay and `agent_lost` on heartbeat loss are M24.
- Monitoring starts on `monitor.start` (sent by the app when the server says the student is Active) and stops on `monitor.stop` (submitted or ended).

**Internet toggle (WFP, service only)** — milestones M21a/M21b
- On `net.set {blocked:true, allow}` from the verified app, the service opens a **dynamic** WFP session (`FWPM_SESSION_FLAG_DYNAMIC`) and adds outbound filters on `FWPM_LAYER_ALE_AUTH_CONNECT_V4/V6`: permit loopback, DHCP and the `allow` addresses (the teacher PC from the pinned session, all ports so WebRTC works), block everything else, on all interfaces. Higher-weight permits win over the block.
- Removal: `net.set {blocked:false}`, `monitor.stop`, service stop, and a **lease**: the app re-sends the current state with every heartbeat; no app contact for 3 minutes removes the filters. A dynamic session's filters disappear by themselves if the service process dies, and on start the service deletes any ExamGuard-tagged persistent filters left by an older build.
- **Wiring (M21b):** `net_control.rs` owns the `NetBlock`; the pipe worker calls it for each `net.set` and a 500 ms timer calls `tick` for the lease. The student app (`InternetController`) turns the server's `state.internet` into `net.set` for the pinned teacher address and repeats it with every heartbeat while blocked. A stopping agent releases the block. The M21a `--console --net-block` switch no longer exists.
- **Built in M21a** (`net_rules`, `wfp_filter`, `wfp_engine`, `net_block`): the filters are on `ALE_AUTH_CONNECT_V4/V6` only, permit weight 10 and block weight 1 in one sublayer. Only a dynamic session is used, so there is nothing persistent to clean up at service start. IPv4 allow addresses only; an empty list is refused. Whether connections that are already open survive a connect-layer block is open until the laptop run (progress.md, M21a).
- Every change is reported as `internet_blocked` / `internet_allowed` evidence. If adding filters fails (e.g. group policy), it reports `internet_block_failed` and the dashboard shows that PC as not blocked.

**What the agent never does:** close or block apps, change the hosts file or proxy, add persistent firewall rules, change network adapters, or install drivers. Its only network change is the temporary internet-off filters above.

**Dev:** `eg-agent --console` runs the service logic (both pipes and the helper supervisor) in the current user session, without SCM, with the same pipe names (stop the real service first). The student app may then use it with `EG_AGENT_CONSOLE=1` (skips the SCM check of the service) and the agent is told which program may connect with `EG_ALLOWED_APP=<path to electron.exe>` (console mode only; the service only reads the registry). The student app also has a fake agent (`EG_FAKE_AGENT=1`) with the same interface and no pipe; `EG_FAKE_AGENT_FAIL=helper|capture|down` makes it report that failure.

## 4. Local code runner (student PC)
- Lives in Electron main (`apps/desktop/src/main/runner/`). Language definitions are config entries: `{ id, label, fileName(code), compile?: argv[], run: argv[], monacoLanguage }`. Python (M15d) is such an entry (id `py`); Java (Stage 2) will be another.
- Toolchains under `apps/desktop/resources/toolchains/`, fetched in dev by `pnpm fetch-toolchains` (`scripts/fetch-toolchains.mjs` + `scripts/toolchains/`, pinned URL + checksum, one version marker per part): `mingw64` (WinLibs portable, UCRT, gcc 16.2, trimmed to C/C++ by the deny-list in `toolchains/mingw.mjs`), `msys64` (MSYS2 base 20260927, keyring set up at fetch time, used only for `pacman`) `npm` (11.21.1) and `python` (python-build-standalone CPython 3.13.17 `install_only`, with tkinter and pip; test suite, IDLE, turtle demos and `.pdb` files removed at fetch time, 144 → 59 MB). JS runs `ExamGuard.exe` with `ELECTRON_RUN_AS_NODE=1` (the RunAsNode fuse stays enabled, see progress.md). Dev overrides `EG_RUNNER_PATH` / `EG_MINGW_DIR` (ignored when packaged).
- gcc passes `default-manifest.o` to the linker unquoted, so a MinGW folder with spaces breaks linking. C/C++ compile with `-specs=eg.specs`, a copy of the pinned gcc's `endfile` spec without the `%:if-exists`, written into the work dir (`runner/gcc-specs.ts`). `fetch-toolchains` also writes the same fix as gcc's own `lib/gcc/x86_64-w64-mingw32/16.2.0/specs` (from `gcc -dumpspecs`). gcc reads that file instead of its built-in specs, so plain `gcc` in the exam terminal links too. Re-check both when the toolchain changes.
- Work dir: `%LOCALAPPDATA%\ExamGuard\run\<examStudentId>\<questionId>\<lang>\`, wiped before each run. The source (and `eg.specs`) is written there and commands run with it as cwd. `examStudentId` is unique per exam and student, and is what the student's main knows.
- Every compile and run goes through `eg-runner.exe --mem <MB> --time <ms> [--procs N] --report <file> -- <argv>`. eg-runner creates a Job Object (`JOB_OBJECT_LIMIT_PROCESS_MEMORY`, `ACTIVE_PROCESS` = 8, `KILL_ON_JOB_CLOSE`, `DIE_ON_UNHANDLED_EXCEPTION`, no crash dialog), starts the child suspended, assigns it to the job, resumes it, passes its stdio through and enforces wall time. Limit hits come from the job's completion port. Its exit code encodes the reason: 0 ran, 10 time, 11 memory, 12 process limit, 20 could not start, 2 bad arguments. The `--report` JSON adds what the exit code can't carry: `{reason, exitCode, timeMs, peakMemMb, error}`. A process-limit hit wins over the time limit (a fork loop usually runs into both). Node enforces the 64 KB output cap (stdout + stderr) and Stop (kills eg-runner, and the job dies with it).
- Limits: run 10 min wall time (the program runs in a console the student types into, or opens a window, so Stop is the normal way out; changed from 5 s in M15c) / 256 MB; compile 15 s / 1024 MB; 8 processes; 64 KB output (`RUN_LIMITS` in `packages/shared`). Under the memory limit an allocation fails (C `malloc` returns NULL, C++ throws), and the run is reported as `memory_limit`.
- One run at a time, with a 2 s gap after the previous run ends. Main refuses a run unless the exam is `running` and the language is allowed for that code question. gcc output is parsed (`file:line:col: error|warning|note: msg`, student file only) into Monaco markers. Each run produces a `run_executed` event (`{questionId, language, mode, flags, status, exitCode, timeMs}`).

**Exam terminal and workspace** — milestones M15a–M15d (M15a spike done 2026-10-21, code in `apps/desktop/src/main/terminal/`)
- Per student exam: `%LOCALAPPDATA%\ExamGuard\run\<examStudentId>\workspace\` holds installed packages and survives between runs: `node_modules`, MSYS2 packages in `.msys\`, and Python `site-packages` via `pip --target` (M15d). ExamGuard's own files sit next to it in `.examguard\` (shims, `pacman.conf`, keyring copy). Per-run folders stay next to it and are still wiped per run.
- Terminal: node-pty 1.1 (its N-API prebuilds load under Electron 44, no rebuild) with `useConptyDll`, which uses node-pty's bundled conpty.dll + OpenConsole.exe; both must stay outside the asar (M45). It spawns `eg-runner --shell --mem 2048 --time 0 --procs 64 -- powershell.exe -NoLogo -NoProfile` as the student user in the workspace (`TERMINAL_LIMITS`).
  - `--time 0` means no wall time.
  - `--shell` makes eg-runner ignore Ctrl+C/Ctrl+Break with a handler routine, which is not inherited, so Ctrl+C stops the student's command and not the job.
  - Closing the pty ends eg-runner, and `KILL_ON_JOB_CLOSE` takes every process the student started (checked with a background `ping -t`).
  - The pty lives in student main (`TerminalHost`, output batched about 16 ms). The renderer's xterm.js dock gets text over IPC only: `terminal:status|open|input|resize|close`, pushes `terminal:data|exit`, Zod schemas in `packages/shared/src/app/terminal.ts`.
  - It closes when the exam leaves `running`, when the teacher turns it off (M15b) and on quit.
- PATH: shims → MinGW `bin` → `workspace\.msys\ucrt64\bin` → `workspace\node_modules\.bin` → system PATH. `ELECTRON_*`, `EG_*` and `VITE_*` variables are removed. `C_INCLUDE_PATH`, `CPLUS_INCLUDE_PATH` and `LIBRARY_PATH` point at `workspace\{include,lib}` and then `.msys\ucrt64\{include,lib}` (M15c), so `gcc cube.c -lfreeglut -lopengl32 -lglu32` works after `pacman -S` with no extra flags.
- Shims (`.cmd`, `terminal/shims.ts`):
  - `node` = `ExamGuard.exe` with `ELECTRON_RUN_AS_NODE=1`, so no separate Node is bundled.
  - `npm` / `npx` = the bundled npm through that shim.
  - `pacman` = the bundled `usr/bin/pacman.exe` with `--root`, `--dbpath`, `--cachedir` and `--logfile` in `workspace\.msys`; `--gpgdir` = the workspace's keyring copy (gpg writes lock and trust files); `--config` = a `pacman.conf` with only `[ucrt64]` (it matches the WinLibs UCRT gcc); and `--noscriptlet`. The first call runs `-Sy`.
  - MSYS2 programs need POSIX paths (`/c/...`): MSYS2's gpg treats `C:/...` as relative.
  - The bundled MSYS2 tree is never written, so it can live read-only under Program Files. Tested with a read-and-execute-only ACL and a standard-user token.
- Toolchain choice (M15a): WinLibs gcc stays, and MSYS2 is used only as a package manager into the workspace. MSYS2's own UCRT gcc would still need a per-student root (the install folder is read-only), and it would replace the pinned gcc.
- Teacher switch (M15b): the terminal exists only while the exam is `running` and the server's `state.terminal` is on. Off by default.
  - The server keeps the switch on `exams` (`TerminalSwitch`, `hosting/terminal-switch.ts`) and pushes every change to all connected students. "On for N minutes" chosen before Start counts from Start. Chosen while running, it counts from now. A timer at `until` (with the 1 s deadline watcher as a backstop, both re-armed on resume) turns it off.
  - Student main (`terminal-gate.ts`) closes the pty as soon as a state no longer allows it, with exit reason `turned_off`. It also keeps its own timer at `until` (local clock + offset) in case the push is late. The Job Object then kills everything started from it. Measured under 1 s with a background `ping -t`.
- Command logging (M15b): PowerShell starts with `-NoExit -Command ". '<.examguard\init.ps1>'"`. The script is rewritten on every open with a random nonce (`terminal/shell-init.ts`).
  - The script sets a PSReadLine `AddToHistoryHandler`. The handler writes `ESC ] 6973 ; <nonce> ; <base64 UTF-8 line> BEL` for each accepted line: as finished by Tab completion, history recall or Ctrl+R, and before it runs. `HistoryNoDuplicates` is off, so a repeated line is reported again. History is not saved. Without PSReadLine, a `prompt` function reports the last history entry instead.
  - ConPTY passes the OSC through. `CommandMarkerParser` takes it out of the stream (also when it is split across chunks) before the renderer and the transcript see it. A marker with another nonce stays ordinary text.
  - Each line becomes a `terminal_command` event (≤2000 chars). Lines with `npm i|install|add`, `pip install`, `python -m pip install` or `pacman -S…` also produce `package_installed` (what was typed, not whether it worked; `parse-install.ts`).
  - A student can remove the handler, but the line that does so is reported first. The transcript keeps everything that was shown either way.
- Transcript (M15b): the output as the student saw it (it includes the echoed input, ANSI kept). `TranscriptBuffer` sends it as WS `transcript` chunks (≤16 KB, about every 2 s, keys `<run id>:<n>`, client cap about 1 MB). Unacked chunks are re-sent after each welcome. The server keeps them in `terminal_chunks` up to 1 MB per student. The teacher opens a student's log from the roster ("Terminal"), also after the exam ended: a command list plus the transcript replayed in a read-only xterm.js.
- `terminal_opened` and `terminal_closed {reason}` events mark each shell.
- Runs (M15c): a run gets the terminal's environment (`terminalEnv`, one builder for both, ExamGuard variables removed). PATH holds MinGW, `workspace\.msys\ucrt64\bin` (so a pacman DLL such as freeglut.dll loads) and `workspace\node_modules\.bin`. `C_INCLUDE_PATH` / `CPLUS_INCLUDE_PATH` / `LIBRARY_PATH` list `workspace\include|lib` first (a header and library the student unpacked there, e.g. graphics.h + libbgi.a) and then `.msys\ucrt64\include|lib`. `NODE_PATH` is `workspace\node_modules` (CommonJS only; ESM `import` ignores it). `PYTHONPATH` and `PIP_TARGET` are `workspace\site-packages` (M15d), with `site-packages\bin` on PATH, so `pip install` needs no flags and Run finds the package.
  - Own flags: the request carries `flags` (≤500 chars). `runner/split-flags.ts` splits it into argv (spaces, `"…"` and `'…'`, no backslash escapes, no shell). C/C++ compile = `gcc -specs -std -O2 -Wall main.c <flags> -o main.exe`, so `-l` libraries link, the student's `-std=` wins and our `-o` stays last. JS = `electron(as node) -r ./eg-stdin.cjs <flags> main.js`. The preload `eg-stdin.cjs` (`runner/js-stdin.ts`) replaces `process.stdin` with the real console input (`CONIN$`) because Electron's executable is a GUI program and its stdin otherwise reads end-of-file at once, so `readline` never saw typed input. The flags are kept per question and language in the renderer's answer store (M16 autosaves them) and shown in the run panel.
  - One run path (no mode switch, so a student has nothing to choose). The compiler runs piped (15 s). The program runs in a node-pty pseudo-console under `eg-runner --shell … --time <RUN_LIMITS.timeMs>` (`runner/pty-run.ts`). Prompts show at once and keys reach the program, so a `scanf` menu works with no stdin box. A window program (GLUT, graphics.h) just opens its own window, because eg-runner restricts no UI and starts the child without a hidden window. Stop closes the job. `--shell` lets Ctrl+C reach the program and not the job. stdout and stderr are one stream (the Errors tab shows compile output). `pty-run` enforces the 64 KB cap and Stop, the Job Object the rest. The renderer's xterm.js `ProgramConsole` gets `runner:data` and sends `runner:input|resize` (fire-and-forget, Zod-checked). The wall time is `RUN_LIMITS.timeMs` until Settings gets a teacher value.
- Python (M15d): `py` runs `python.exe <flags> main.py` in the same console as the others (no compile step, `languages.ts`). The `python`, `python3`, `pip` and `pip3` shims come first on PATH (the Windows Store `python` alias cannot take over) and run the bundled interpreter; pip is always `python -m pip`. Run sets `PYTHONUTF8=1`, `PYTHONDONTWRITEBYTECODE=1` and one thread for OpenBLAS/OpenMP/MKL: NumPy otherwise reserves a buffer per CPU core at import, and on a 20-core PC that alone passes the 256 MB limit. With that, NumPy and a matplotlib (TkAgg) window run inside the limits. `MPLCONFIGDIR` is `workspace\.mpl`. Python syntax errors show as a traceback in the console; there are no editor markers for them. Java (trimmed JDK, jars from `workspace/lib`) is Stage 2.
- Project folder and Files panel (M15e): the program's cwd is `workspace\` (`code-runner.ts`), the same folder as the terminal, so `open('data.txt')`, `fopen` and `savefig` use the student's own files and they survive between runs. The wiped `<questionId>\<lang>\` folder keeps the source (passed to the language by full path), the build output, `eg.specs`, `eg-stdin.cjs` and the report. `terminalEnv` adds the workspace to `PYTHONPATH`, `NODE_PATH` and the C/C++ include path, so `import helper`, `require('helper')` and `#include "helper.h"` find a file saved there; a relative `require('./x')` from `main.js` does not, because `main.js` lives in the run folder. The Files panel is `FilesPanel` (lazy, mounted on first open and then hidden) over `files:list|read|write|create|rename|remove` IPC (`apps/desktop/src/main/files/`): `resolveInside` rejects `..`, absolute paths, drive letters, reserved Windows names and links/junctions that lead out of the workspace, `WorkspaceFiles` does the work, and every call answers `{ok:true,value}` or `{ok:false,message}`. Limits (`FILE_LIMITS`): 2 MB per text file, 10 MB per previewed image, 200 MB of the student's own files checked on save and create (a running program is not limited, the Job Object has no disk limit), 1000 entries per folder. `node_modules`, `site-packages` and dotfolders are hidden unless asked and not counted. Images are shown as `data:` URLs in an `<img>`. Text files open in a separate Monaco model and save by themselves 0.6 s after typing stops. The panel is available only while the exam runs and the teacher's `filesEnabled` is on (`filesRefusal`); files are local only and are not part of the submission.
- Teacher-provided exam files (M15f): the teacher attaches files to a draft or ready exam (`ExamFilesSection`, raw `application/octet-stream` upload with `?name=`). The server keeps the manifest in `exam_files` and the bytes in `<dataDir>/exam-files/<examId>/<fileId>` (`ExamFileService` over `ExamFileRepo` and `ExamFileStore`); names are checked with the shared `checkFileName`, a file with the same name in any letter case replaces the old one, and the limits are `EXAM_FILE_LIMITS` (25 MB per file, 50 MB and 50 files per exam). The manifest travels in `SessionState.examFiles` (empty when the Files switch is off); the bytes never use the WS (512 KB frames) but `GET /api/v1/exam-files/:fileId` over the pinned HTTPS connection with the session token. Student main (`ExamFileSync`, called from the `onExam` hook in `ipc.ts`): while the exam is `hosting` or `running` each file not yet present is downloaded (2 at a time, 3 tries, `downloadExamFile` streams to `<name>.part`, counts and hashes the bytes and renames only if the size and SHA-256 match) into `%LOCALAPPDATA%\ExamGuard\run\<examStudentId>\.examguard\exam-files\<fileId>`. When the exam is `running`, each staged file is copied into the workspace root (`COPYFILE_EXCL`, name checked and resolved with `resolveInside`) and its id is recorded in `revealed.json` next to it, so a file the student deleted is not copied again after a reconnect or restart and a file of that name the student already has is left alone. After that the files are ordinary project files. A failed download is shown in the lobby and the exam screen with Try again.
- Bundle size (2026-10-21, measured on the dev PC): Electron runtime 369 MB; WinLibs MinGW unpacked 947 MB, **535 MB after the C/C++ trim** (measured in M15a); MSYS2 base 225 MB unpacked (not trimmed yet, M45); npm 12 MB; CPython 59 MB after trimming (144 MB as fetched, M15d). Estimated totals: about 0.9–1.1 GB installed, 300–400 MB installer download. One installer always contains everything.

## 5. Screens: thumbnails and live view
- **Capture** happens in student Electron main with `desktopCapturer` (`types: ['screen']`) for the whole screen. The helper's screenshots are only for events.
- **Thumbnails:** the teacher UI tells the server which students are on the visible page (`thumbs.subscribe`, about 25–30 IDs). The server sends `thumb.start {intervalMs: 4000}` to those students and `thumb.stop` to the rest. A student encodes a 320 px JPEG (`nativeImage.toJPEG`, q≈50, about 10–20 KB) and sends it as a binary frame. The server keeps only the latest frame per student in memory and forwards it to the teacher socket. Budget: 30 × 15 KB / 4 s ≈ 110 KB/s, well under the 1 MB/s target. With 200 on one page it would still be ~750 KB/s. Nothing is stored.
- **Live view (one student at a time, max 2 open):** teacher clicks → `live.request` → the student creates an `RTCPeerConnection`, adds a `getUserMedia` desktop track (chromeMediaSource, max 1280 px, 8 fps) and sends an offer. Offer, answer and ICE travel as `rtc.signal` through the server. The teacher renderer plays it. Closing it (or 60 s without the panel visible) sends `live.stop`. The deferrable fallback if WebRTC slips is a "fast thumbnail" mode: 960 px every 1 s over WS for the selected student.

## 6. Autosave, offline, resume, recovery
- **Answer key:** `(questionId, language)`. Written answers use language `text`. The client keeps a buffer per key and a monotonically increasing `clientSeq` per session.
- **Autosave triggers:** every 10 s if the content changed, plus Run, question switch, language switch and submit. Each save becomes an `answer_versions` row. The server dedupes on `(exam_student_id, client_seq)` and acks the `clientSeq` after the commit. `clientSeq` is one counter per student; after every welcome the client continues past the largest `clientSeq` in `welcome.saved`, so a restarted app never reuses a number. The scheduler is in the renderer (`Autosaver`), main numbers the saves and keeps the unacked ones (`AnswerOutbox`).
- **Offline queue (M17):** every save, event and transcript chunk is also appended to a JSONL file in userData (`queue/<examStudentId>.jsonl`, `main/resume/offline-queue.ts`). Each line is encrypted with `safeStorage` (DPAPI, user-scoped); an ack appends a `-<key>` line and an empty queue deletes the file. The frames stay in memory too and are re-sent after every welcome until acked; the file only matters after a restart, when `SessionClient.start` loads it. If encryption is unavailable nothing is written (never plaintext). A write that fails is logged and never stops the exam.
- **Reconnect:** WS reconnect with backoff (0.5 s → 5 s, jitter). The token is reused. The server replays the state snapshot (`session.state`). A watchdog drops a socket that has been silent for three ping periods, so a cable pull shows as "reconnecting" within about 15 s.
- **Clock:** the client estimates the server offset from `ping/pong` RTT. Client timestamps (`clientTs`) are in server time.
- **Deadline:** `deadline = exam.started_at + duration + exam_student.extension_sec + exam.global_extension_sec`, the same for late joiners. "Ending" is not a stored state (M18): between a student's deadline and `deadline + grace` the exam and the student stay `running`/`active`, and the save gate accepts only saves with `clientTs ≤ deadline` that arrive within the grace (`monitoring.graceSec`, default 60 s). A 1 s watcher (`DeadlineWatcher`) then finalizes each working student at their own `deadline + grace`, and ends the exam at `last deadline + grace`; after a restart the first tick does the same for deadlines that passed while the server was down. Finalizing (`SubmissionService`, the same path for the student's Submit, the auto-submit and the teacher's End) flushes the batch writer, takes the newest selected-language version per question (an empty answer for an unanswered question), writes `final_answers`, hashes them into the receipt and sets the student `submitted` (`ended_by_teacher` after a manual End), all in one transaction guarded by the student state, so it happens once. Trusting the client stamp is an accepted risk (see progress.md).
- **Same-PC resume:** `deviceId = SHA-256(HKLM MachineGuid + "examguard")`. Join with the same student ID and the same device while a session exists means the token is re-issued and the session resumes. A different device is rejected and logged (critical `duplicate_login`) until the teacher resets the session. After a restart the app resumes without the PIN: the session file (`session/session.enc`: token, pinned address and fingerprint, names) is loaded in student main, the socket reconnects with the same token, and the renderer asks main to restore the editors (`answers:restore`). Main merges the server's newest version of each buffer (`GET /answers/latest`, asked only when the welcome says versions exist) with the unacked saves from the queue; the higher `clientSeq` wins per buffer and for the selected language. The exam screen waits for this ("Restoring your work…", with Retry) so the student cannot type over work that is safe on the server. The student can also choose **Leave this exam** while the link is down; that removes the session file but keeps the queue. The session file is removed on `unauthorized` (token no longer valid) and when the exam ends.
- **Server crash or restart:** all state is in SQLite (WAL, `synchronous=NORMAL`). On boot the server finds exams in Hosting/Running, restarts listeners with the same cert, port and PIN, recomputes deadlines from stored timestamps (the timer kept running while it was down) and re-advertises mDNS. Students reconnect automatically. Deadlines that passed during downtime are processed straight away with the grace rule.
- **Batching:** events and autosaves are buffered in memory and written in one transaction every 250 ms or every 200 items. Acks are sent after commit.

## 7. AI grading pipeline (teacher server)
```
GradingProvider { id; gradeAnswer(input: GradingInput, opts): Promise<ProviderResult /* raw text + usage */> }
```
- `apps/server/src/grading/`: `providers/gemini.ts` (`@google/genai`, JSON response schema, temperature 0.1), `providers/fake.ts` (replays fixtures from `fixtures/grading/*.json`, used by all tests), `prompt.ts` (versioned template, `PROMPT_VERSION`), `validate.ts` (Zod + rules: each `awarded ≤ max`, half-unit steps, criteria names match the guide, total = sum), `pipeline.ts`.
- **Flow:** "Evaluate with AI" → one `grading_jobs` row per question → for each question, every final answer goes through a p-limit queue (concurrency 4, configurable) → retries with exponential backoff on 429/5xx (3×) → invalid output gets 2 retries with a repair hint → after that the answer is `needs_manual`. Each attempt stores an `evaluations` row (provider, model, prompt version, raw response).
- **Input** has only an anonymous ID (`exam_student.anon_id`), never name or student ID.
- The API key is decrypted in main and sent to the server over the utilityProcess message port at grading time. It's never written to the DB or logs.
- Progress goes out through WS `grading.progress`. The pipeline is resumable: on restart, unfinished answers in a job are picked up again.
- **Re-evaluate with an instruction:** same pipeline plus the teacher instruction in the prompt. Scope: one answer, or all answers on that question except Verified/Modified unless included.
