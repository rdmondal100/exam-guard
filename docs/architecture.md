# Architecture

Scope: how the pieces fit together. Tables are in `data-model.md`, message shapes in `protocol.md`, build order in `milestones.md`. Behaviour rules (what counts as an event, severities, limits) come from `requirements.md`. This doc only says *how* they're implemented.

## 1. Processes

### Teacher PC (ExamGuard Teacher)
| Process | Role |
|---|---|
| Electron main (`apps/desktop/src/main`) | Window, teacher login gate, `safeStorage` (API key, secrets), power-save blocker while hosting, starts/restarts the server |
| Renderer (teacher UI) | React app. Talks to the server over **loopback HTTP/WS** (`127.0.0.1:47821`) with a teacher token handed over by preload |
| Server (`apps/server`, Electron `utilityProcess`) | Express 5 + `ws`. Two listeners: student HTTPS/WSS `0.0.0.0:47820` (on only while hosting) and teacher loopback `127.0.0.1:47821` (always on). Owns SQLite, mDNS advertising, the exam timer, event classification, risk score, thumbnail fan-out, WebRTC signaling and the grading pipeline |

Main restarts the server on exit with backoff (1 s, 2 s, 5 s, then every 10 s). Each restart is logged and shown as a banner. If main itself crashes, students reconnect after the teacher relaunches the app (§6).

**Server layout (`apps/server/src`).** `server.ts` is the utilityProcess entry. `container.ts` builds every repository and service once. `app.ts` (teacher, `http.createServer`) and `studentApp.ts` (student, `https.createServer`) are the Express apps. A request passes:
1. `middlewares/`: `cors` and `teacherToken` first (teacher only), then the body parsers.
2. `routes/*.routes.ts`: one Router per resource; `routes/index.ts` mounts the teacher ones under `/api/v1`. Guarded routes add `requireLogin`; student routes that need a session add `verifyStudent`.
3. `controllers/*.controller.ts`: validate with the shared Zod schemas, call services and repositories, and `throw new ApiError(...)` to refuse.
4. `services/<domain>/` (hosting, join, exams, answers, submissions, screenshots, exam-files, auth) and `db/repositories/*.repo.ts` (all SQL).

`error.middleware.ts` turns every error into the `{ error: { code, message, details? } }` envelope: `ApiError` subclasses (`HostingError`, `JoinError`, `ExamFileError`), body-parser errors (`invalid_json` 400, `payload_too_large` 413) and unknown routes (`not_found` 404). Anything else is a 500 `internal`. Each listener's `/ws` upgrade is served by `sockets/wsServer.ts` (`ws` with `noServer`) and never reaches Express. Route tests call `inject()` from `src/testing/inject.ts` (supertest), so no port is opened.

### Student PC (ExamGuard Student)
| Process | Runs as | Role |
|---|---|---|
| Electron main | Student user | Exam window, the monitor (§3), code runner, offline queue, screen capture for thumbnails and WebRTC, clipboard control |
| Renderer (student UI) | Student user | Exam UI and Monaco. No Node access |
| `SiteReader.exe` | Student user | Started for one read of a Chrome/Edge address bar (§3), then exits |
| Student program | Student user | One code run, a plain child process (§4) |

There is no service, no agent and no Rust on a student PC (removed 2026-11-12; the app never changes the PC).

### Two apps, two installers (M45–M46, M52)
`apps/desktop` builds two apps: `electron-vite --mode teacher|student` sets the compile-time `__EG_APP__`, and `main/index.ts`, the preload and `App.tsx` load the app's own code (`main/teacher/startTeacher.ts`, `main/student/startStudent.ts`, `TeacherGate` / `StudentFlow`) through constant branches with dynamic imports, so the other app's code is not in the bundle. The preload exposes the common methods plus the app's own (`exposedIn`). There is no mode choice and no install type any more.

`pnpm package [--app teacher|student]` (`scripts/package-desktop.mjs`) builds each app, copies the desktop app with its production dependencies into `release/stage` (`pnpm deploy --legacy --ignore-scripts`, hoisted `node_modules`), prunes what that app does not use (`FLAVORS.dropDependencies` and everything only they reach, `keepClosure`), and runs electron-builder with `builderConfig(paths, app)` into `release/<app>/`. Measured 2026-11-12: Teacher 419 MB installed (no toolchains, node-pty or get-windows; RunAsNode off), Student about 1.1 GB (no server, SQLite or Gemini SDK). The rest of this section describes the student app's layout. Renderer-only packages are dev dependencies, because Vite bundles them. Layout under the install folder (per machine, default `C:\Program Files\ExamGuard`): `ExamGuard.exe`, `resources\app.asar` (main, preload, renderer, the server package and its dependencies; node-pty, better-sqlite3 and get-windows in `app.asar.unpacked`), `resources\SiteReader.exe`, `resources\toolchains\` (MinGW, MSYS2 without its translations and manuals, npm, Python). Fuses: RunAsNode on for the student app (student JavaScript) and off for the teacher's, `NODE_OPTIONS` and `--inspect` off, asar integrity checked, app only from the asar. userData: the teacher app keeps `productName` ExamGuard (`%APPDATA%\ExamGuard`), the student app is `%APPDATA%\ExamGuard Student`.

`apps/desktop/resources/teacher.nsh` adds the two firewall rules (§2); `student.nsh` does nothing more than remove what an older version may have left: the `ExamGuardAgent` service (`sc stop` / `sc delete`, no-op when there is none) and `HKLM\Software\ExamGuard` (the old install type). **Uninstall** (also run by an upgrade, before the files are replaced): removes the rules and any old service; a real uninstall also deletes `HKLM\Software\ExamGuard` and `%ProgramData%\ExamGuard` (what the old agent left). An unticked choice on the uninstaller's components page deletes this Windows user's `%APPDATA%\ExamGuard` and, if Settings moved the data folder there, its known entries (only when it holds `db\examguard.sqlite`); a silent uninstall keeps the data.

## 2. Networking
- **Student → server:** HTTPS for join and bootstrap, then one WSS connection per student (`/ws`). It carries JSON frames, plus binary frames for thumbnails and screenshots. Port 47820 by default, configurable in Settings.
- **Discovery:** the server advertises `_examguard._tcp` over mDNS (bonjour-service) while hosting. TXT record: `v` (protocol), `exam` (title), `fp` (SHA-256 cert fingerprint, base64url). The student app lists every host it finds. Manual entry of `IP[:port]` is always available (teacher on Wi-Fi, different subnets).
- **TLS:** the teacher app generates one ECDSA P-256 self-signed cert per installation (`certs/`) and regenerates it on request. The student app pins the fingerprint:
  - via mDNS: the `fp` from TXT must match the presented cert
  - via manual IP: trust on first use for this exam. The student screen shows a **4-character code** (first 20 bits of the fingerprint, Crockford base32) next to the PIN field, and the teacher's hosting screen shows the same code. Invigilators compare them by eye.
  - the pinned fingerprint is stored with the student's session, so a reconnect to a different cert is refused.
- **Teacher UI → server:** loopback only, plain HTTP. The token is random per app launch, passed from main to the utilityProcess and to preload. Never bound to the LAN. HTTP calls send it in the `X-Teacher-Token` header; the WebSocket (`/ws`) takes it as `?token=` because a browser WebSocket cannot set headers.
- **WebRTC:** peer-to-peer on the LAN using host candidates only (no STUN/TURN, no internet). Signaling is relayed over the existing WS connections.
- **Firewall:** the installer adds program-based inbound rules `ExamGuard (TCP-In)` and `ExamGuard (UDP-In)` for `<install dir>\ExamGuard.exe`, profiles Domain + Private, on Teacher installs only (removed again on uninstall or a reinstall as Student). Student PCs make outbound connections only. ICE checks from the student side open the stateful path. ExamGuard never changes a student PC's network.
- **Limits:** WS max frame 512 KB (screenshots are chunked if larger). Per-token rate limits on saves/events, and a per-IP limit on `/join` that counts failed tries only (5 wrong PINs or unknown IDs per minute, then 429 `rate_limited` with `retryAfterSec`), so a lab behind one address is not throttled. Every inbound frame passes `safeParse` against `packages/shared`.

## 3. Monitoring (in the student app)

The Rust agent (service, helper, pipe, WFP internet switch, tamper lock, relaunch) was removed on 2026-11-12. Student main monitors by itself, in `apps/desktop/src/main/tracking/`, laid out like the WorkPulse reference app. It only reads: it never blocks, closes or changes anything and never touches the network. `tracking/index.ts` wires it to Windows; every other file is pure and tested with fakes.

- **Window in front (`foreground.ts`):** get-windows `activeWindow()` (native N-API, `PROCESS_QUERY_LIMITED_INFORMATION`, so elevated windows such as Task Manager are readable) → exe name, path, pid, window handle, title, bounds. `null` when nothing can be read (lock screen, secure desktop, a switch in progress). Loaded with a dynamic `import()` because it is ESM with a native binary; kept out of the asar (`asarUnpack`).
- **Website (`site.ts` + `resources/SiteReader.cs`):** for `chrome.exe` / `msedge.exe` only, `SiteReader.exe <hwnd>` reads the address bar through UI Automation (class `OmniboxViewViews`, the same in every language) and prints `address <text>`, `typing` (the student is in the bar: the last site of that window stays), `private` (Incognito/InPrivate, matched on the profile button's label; the address is never read) or `none`. 800 ms timeout. It is read only when the window or its title (digits ignored) changes. The text becomes `{domain, url}`: the registrable domain via tldts (private suffixes count, so `myapp.vercel.app` is its own site; localhost and IPs as they are) and the full address (≤2048 chars). `SiteReader.exe` is built by `apps/desktop/scripts/build-site-reader.mjs` with `csc.exe` from .NET Framework 4 (ships with Windows), on every `dev` and `build` when the source is newer.
- **Inside or outside (`inside.ts`):** inside = the app's own process, a process the app started for the student (`OwnProcesses`: the program of a run, the compiler, the terminal's shell), or a program under `%LOCALAPPDATA%\ExamGuard\run` or the bundled toolchains (a GUI program started from the terminal). Everything else is outside.
- **Switch policy (`policy.ts`, `SwitchPolicy`, ported from the old `policy.rs`):** a new outside window → `focus_lost`; a new title or site in the same outside window → `title_changed`; every `periodicOutsideSec` (20 s) while outside → `still_outside`; back inside → `focus_returned` with `durationMs` from the first outside window. Shots at the switch, on a title change and periodic, at most one per `minShotGapSec` (5 s). The exam's `monitoringPolicy` from the server drives it.
- **Tracker (`tracker.ts`):** reads the window in front every 1 s (a slow read skips a tick) and the open windows every 2 s, follows Electron `screen` (`display-added/removed`) and `powerMonitor` (`lock-screen`). Evidence goes out in the order seen, after its screenshot (`screenshots/capture.ts`: Electron `desktopCapturer`, the screen the window is on, ≤`maxWidth` 1600 px, JPEG quality 60).
  - **Launches (`openApps.ts`, `AppWatch`):** the first look is `processes_at_start` (programs with a window, one per process, ≤300); later looks report a process whose first window appeared as `app_launched` (`taskmgr.exe` → `taskmgr_opened`). A process stays known while it runs (`process.kill(pid, 0)`), so hiding and showing a window is no launch. Windows' own shell hosts (Start, search, touch keyboard, lock app) and the student's own programs are skipped. Programs without a window are not seen.
  - **Screens:** more than one at the start → `monitor_changed {monitors}`; a change → `monitor_changed {monitors, monitorsBefore}`.
  - **Secure desktop:** the lock screen → `secure_desktop {desktop:'lock'}`; no readable window for 2 s → `secure_desktop {desktop:'secure'}` (Ctrl+Alt+Del, a UAC prompt), once until a window is readable again.
- **Exam monitor (`examMonitor.ts`):** starts the tracker when the server's state says the student works on a running exam (`wantsMonitoring`), restarts it on a new policy, stops it on submit or end. Each piece of evidence gets the key `<examStudentId>:<runId>:<n>` (`runId` random per app run), sent with `SessionClient.sendEvidence`: the screenshot as binary frames before the `event`, re-sent after every welcome until `event.ack`, and the event (without the picture) in the encrypted offline queue, so a restart loses only pictures. The server stores it as source `monitor` with key `monitor:<key>` (protocol §3).
- **Self-check (`monitorCheck.ts`):** a 160 px test capture, the screen count and up to 3 reads of the window in front. Run before each join (the app refuses locally with `monitor_required`; the server refuses a `monitor` block that fails `monitorProblem`), at app start in Student mode, and re-sent with the new count when screens change. After each welcome the app sends it as `monitor.status`, which drives the roster's `monitorOk` and screen count.
- **What it never does:** block or close apps, change the network, firewall, hosts file or proxy, install a service or driver, or ask for elevation. If the student ends ExamGuard, monitoring stops with it; the server sees the socket close and records `network_lost` (there is no relaunch and no tamper lock).

**Clipboard and paste (M25, in the app)**
- Main empties the system clipboard when the student starts working on the exam (`main/clipboard/clipboardClear.ts`, on the `examWorking` edge; again after an app relaunch).
- The renderer's paste guard (`hooks/usePasteGuard.ts` + `lib/pasteGuard.ts`) covers the whole exam screen: editors, answer boxes, Files editor, input fields, program console and terminal. Capture-phase `copy`/`cut` listeners on `window` remember the selection and wrap the event's `clipboardData.setData`, so the text Monaco and xterm write is remembered too (FNV-1a + length of the CRLF-normalised text, last 500). A capture-phase `paste` (or `drop` of text not dragged inside the window) whose text is not remembered is cancelled before Monaco or xterm see it, a short notice shows, and main logs `paste_blocked` (at most one per 2 s, the rest folded into `suppressed`).
- The default session denies the `clipboard-read` permission (`main/window/mainWindow.ts`), so Monaco's menu Paste cannot fall back to `navigator.clipboard.readText()` past the guard.

## 4. Local code runner (student PC)
- Lives in Electron main (`apps/desktop/src/main/runner/`). Language definitions are config entries: `{ id, label, fileName(code), compile?: argv[], run: argv[], monacoLanguage }`. Python (M15d) is such an entry (id `py`); Java (Stage 2) will be another.
- Toolchains under `apps/desktop/resources/toolchains/`, fetched in dev by `pnpm fetch-toolchains` (`scripts/fetch-toolchains.mjs` + `scripts/toolchains/`, pinned URL + checksum, one version marker per part): `mingw64` (WinLibs portable, UCRT, gcc 16.2, trimmed to C/C++ by the deny-list in `toolchains/mingw.mjs`), `msys64` (MSYS2 base 20260927, keyring set up at fetch time, used only for `pacman`) `npm` (11.21.1) and `python` (python-build-standalone CPython 3.13.17 `install_only`, with tkinter and pip; test suite, IDLE, turtle demos and `.pdb` files removed at fetch time, 144 → 59 MB). JS runs `ExamGuard.exe` with `ELECTRON_RUN_AS_NODE=1` (the RunAsNode fuse stays enabled, see decisions.md). Dev override `EG_MINGW_DIR` (ignored when packaged).
- gcc passes `default-manifest.o` to the linker unquoted, so a MinGW folder with spaces breaks linking. C/C++ compile with `-specs=eg.specs`, a copy of the pinned gcc's `endfile` spec without the `%:if-exists`, written into the work dir (`runner/gccSpecs.ts`). `fetch-toolchains` also writes the same fix as gcc's own `lib/gcc/x86_64-w64-mingw32/16.2.0/specs` (from `gcc -dumpspecs`). gcc reads that file instead of its built-in specs, so plain `gcc` in the exam terminal links too. Re-check both when the toolchain changes.
- Work dir: `%LOCALAPPDATA%\ExamGuard\run\<examStudentId>\<questionId>\<lang>\`, wiped before each run. The source (and `eg.specs`) is written there and commands run with it as cwd. `examStudentId` is unique per exam and student, and is what the student's main knows.
- Compile and run are plain child processes (eg-runner and its Job Object were removed on 2026-11-12). The compiler is `spawnLimited` (`runner/spawnLimited.ts`): piped, 15 s, the 64 KB output cap. The program is `ptyRun` (`runner/ptyRun.ts`) in a pseudo-console with the run time limit and the same cap. Stop, the time limit and the cap call `killTree` (`taskkill /PID <pid> /T /F`, `runner/killTree.ts`), so whatever the program started ends too; a program that detached itself (`start`, `Start-Process`) can survive. There is **no memory or process limit**.
- Limits: run 10 min wall time (the program runs in a console the student types into, or opens a window, so Stop is the normal way out) and 64 KB output; compile 15 s (defaults: `RUN_LIMITS` / `DEFAULT_RUN_LIMITS` in `packages/shared`). From M43 the teacher sets run time and output in Settings; the values are copied into the exam at hosting start (`exams.run_limits_json`, older snapshots with memory and process limits still parse), sent as `SessionState.runLimits`, and student main's `CodeRunner` reads them per run. The time limit counts from the start of the pseudo-console, which includes ConPTY's start (it holds the program up to 3 s until the terminal answers its DA1 query; the renderer's xterm.js answers at once).
- JavaScript runs on `ExamGuard.exe` as Node, and that executable is a GUI program: as the pseudo-console's own process it gets no console and prints nothing. `cmd.exe /d /s /c "<quoted argv>"` hosts it instead (`runner/cmdHost.ts`): Electron attaches to cmd's console, cmd waits and passes the exit code on, and the tree kill ends both. Flags with `"` or `%` are refused for JavaScript.
- One run at a time, with a 2 s gap after the previous run ends. Main refuses a run unless the exam is `running` and the language is allowed for that code question. gcc output is parsed (`file:line:col: error|warning|note: msg`, student file only) into Monaco markers. Each run produces a `run_executed` event (`{questionId, language, mode, flags, status, exitCode, timeMs}`).

**Exam terminal and workspace** — milestones M15a–M15d (M15a spike done 2026-10-21, code in `apps/desktop/src/main/terminal/`)
- Per student exam: `%LOCALAPPDATA%\ExamGuard\run\<examStudentId>\workspace\` holds installed packages and survives between runs: `node_modules`, MSYS2 packages in `.msys\`, and Python `site-packages` via `pip --target` (M15d). ExamGuard's own files sit next to it in `.examguard\` (shims, `pacman.conf`, keyring copy). Per-run folders stay next to it and are still wiped per run.
- Terminal: node-pty 1.1 (its N-API prebuilds load under Electron 44, no rebuild) with `useConptyDll`, which uses node-pty's bundled conpty.dll + OpenConsole.exe; both must stay outside the asar (M45). It spawns `powershell.exe -NoLogo -NoProfile` itself as the student user in the workspace, with no wall time.
  - Ctrl+C reaches the student's command, as in any console.
  - Closing the terminal kills the shell's process tree (`taskkill /T /F` on the shell), so every process the student started from it ends; the shell's pid also marks its windows as the student's own for the monitor.
  - The pty lives in student main (`TerminalHost`, output batched about 16 ms). The renderer's xterm.js dock gets text over IPC only: `terminal:status|open|input|resize|close`, pushes `terminal:data|exit`, Zod schemas in `packages/shared/src/app/terminal.ts`.
  - It closes when the exam leaves `running`, when the teacher turns it off (M15b) and on quit.
- PATH: shims → MinGW `bin` → `workspace\.msys\ucrt64\bin` → `workspace\node_modules\.bin` → system PATH. `ELECTRON_*`, `EG_*` and `VITE_*` variables are removed. `C_INCLUDE_PATH`, `CPLUS_INCLUDE_PATH` and `LIBRARY_PATH` point at `workspace\{include,lib}` and then `.msys\ucrt64\{include,lib}` (M15c), so `gcc cube.c -lfreeglut -lopengl32 -lglu32` works after `pacman -S` with no extra flags.
- Shims (`.cmd`, `terminal/shims.ts`):
  - `node` = `ExamGuard.exe` with `ELECTRON_RUN_AS_NODE=1`, so no separate Node is bundled.
  - `npm` / `npx` = the bundled npm through that shim.
  - `pacman` = the bundled `usr/bin/pacman.exe` with `--root`, `--dbpath`, `--cachedir` and `--logfile` in `workspace\.msys`; `--gpgdir` = the workspace's keyring copy (gpg writes lock and trust files); `--config` = a `pacman.conf` with only `[ucrt64]` (it matches the WinLibs UCRT gcc); and `--noscriptlet`. The first call runs `-Sy`.
  - MSYS2 programs need POSIX paths (`/c/...`): MSYS2's gpg treats `C:/...` as relative.
  - The bundled MSYS2 tree is never written, so it can live read-only under Program Files. Tested with a read-and-execute-only ACL and a standard-user token.
- Toolchain choice (M15a): WinLibs gcc stays, and MSYS2 is used only as a package manager into the workspace. MSYS2's own UCRT gcc would still need a per-student root (the install folder is read-only), and it would replace the pinned gcc.
- Teacher switch (M15b): the terminal exists only while the exam is `running` and the server's `state.terminal` is on. Off by default.
  - The server keeps the switch on `exams` (`TerminalSwitch`, `services/hosting/terminal-switch.ts`) and pushes every change to all connected students. "On for N minutes" chosen before Start counts from Start. Chosen while running, it counts from now. A timer at `until` (with the 1 s deadline watcher as a backstop, both re-armed on resume) turns it off.
  - Student main (`terminalGate.ts`) closes the pty as soon as a state no longer allows it, with exit reason `turned_off`. It also keeps its own timer at `until` (local clock + offset) in case the push is late. The tree kill then ends everything started from it.
- Command logging (M15b): PowerShell starts with `-NoExit -Command ". '<.examguard\init.ps1>'"`. The script is rewritten on every open with a random nonce (`terminal/shellInit.ts`).
  - The script sets a PSReadLine `AddToHistoryHandler`. The handler writes `ESC ] 6973 ; <nonce> ; <base64 UTF-8 line> BEL` for each accepted line: as finished by Tab completion, history recall or Ctrl+R, and before it runs. `HistoryNoDuplicates` is off, so a repeated line is reported again. History is not saved. Without PSReadLine, a `prompt` function reports the last history entry instead.
  - ConPTY passes the OSC through. `CommandMarkerParser` takes it out of the stream (also when it is split across chunks) before the renderer and the transcript see it. A marker with another nonce stays ordinary text.
  - Each line becomes a `terminal_command` event (≤2000 chars). Lines with `npm i|install|add`, `pip install`, `python -m pip install` or `pacman -S…` also produce `package_installed` (what was typed, not whether it worked; `parseInstall.ts`).
  - A student can remove the handler, but the line that does so is reported first. The transcript keeps everything that was shown either way.
- Transcript (M15b): the output as the student saw it (it includes the echoed input, ANSI kept). `TranscriptBuffer` sends it as WS `transcript` chunks (≤16 KB, about every 2 s, keys `<run id>:<n>`, client cap about 1 MB). Unacked chunks are re-sent after each welcome. The server keeps them in `terminal_chunks` up to 1 MB per student. The teacher opens a student's log from the roster ("Terminal"), also after the exam ended: a command list plus the transcript replayed in a read-only xterm.js.
- `terminal_opened` and `terminal_closed {reason}` events mark each shell.
- Runs (M15c): a run gets the terminal's environment (`terminalEnv`, one builder for both, ExamGuard variables removed). PATH holds MinGW, `workspace\.msys\ucrt64\bin` (so a pacman DLL such as freeglut.dll loads) and `workspace\node_modules\.bin`. `C_INCLUDE_PATH` / `CPLUS_INCLUDE_PATH` / `LIBRARY_PATH` list `workspace\include|lib` first (a header and library the student unpacked there, e.g. graphics.h + libbgi.a) and then `.msys\ucrt64\include|lib`. `NODE_PATH` is `workspace\node_modules` (CommonJS only; ESM `import` ignores it). `PYTHONPATH` and `PIP_TARGET` are `workspace\site-packages` (M15d), with `site-packages\bin` on PATH, so `pip install` needs no flags and Run finds the package.
  - Own flags: the request carries `flags` (≤500 chars). `runner/splitFlags.ts` splits it into argv (spaces, `"…"` and `'…'`, no backslash escapes, no shell). C/C++ compile = `gcc -specs -std -O2 -Wall main.c <flags> -o main.exe`, so `-l` libraries link, the student's `-std=` wins and our `-o` stays last. JS = `electron(as node) -r ./eg-stdin.cjs <flags> main.js`. The preload `eg-stdin.cjs` (`runner/jsStdin.ts`) replaces `process.stdin` with the real console input (`CONIN$`) because Electron's executable is a GUI program and its stdin otherwise reads end-of-file at once, so `readline` never saw typed input. The flags are kept per question and language in the renderer's answer store (M16 autosaves them) and shown in the run panel.
  - One run path (no mode switch, so a student has nothing to choose). The compiler runs piped (15 s). The program itself runs in a node-pty pseudo-console (`runner/ptyRun.ts`; JavaScript through cmd, see above). Prompts show at once and keys reach the program, so a `scanf` menu works with no stdin box. A window program (GLUT, graphics.h) just opens its own window. Stop and the time limit kill the tree. stdout and stderr are one stream (the Errors tab shows compile output). `ptyRun` enforces the time limit, the 64 KB cap and Stop. The renderer's xterm.js `ProgramConsole` gets `runner:data` and sends `runner:input|resize` (fire-and-forget, Zod-checked). The wall time is `RUN_LIMITS.timeMs` until Settings gets a teacher value.
- Python (M15d): `py` runs `python.exe <flags> main.py` in the same console as the others (no compile step, `languages.ts`). The `python`, `python3`, `pip` and `pip3` shims come first on PATH (the Windows Store `python` alias cannot take over) and run the bundled interpreter; pip is always `python -m pip`. Run sets `PYTHONUTF8=1`, `PYTHONDONTWRITEBYTECODE=1` and one thread for OpenBLAS/OpenMP/MKL: NumPy otherwise reserves a buffer per CPU core at import (it mattered under the old 256 MB limit and still keeps memory down). `MPLCONFIGDIR` is `workspace\.mpl`. Python syntax errors show as a traceback in the console; there are no editor markers for them. Java (trimmed JDK, jars from `workspace/lib`) is Stage 2.
- Project folder and Files panel (M15e): the program's cwd is `workspace\` (`codeRunner.ts`), the same folder as the terminal, so `open('data.txt')`, `fopen` and `savefig` use the student's own files and they survive between runs. The wiped `<questionId>\<lang>\` folder keeps the source (passed to the language by full path), the build output, `eg.specs` and `eg-stdin.cjs`. `terminalEnv` adds the workspace to `PYTHONPATH`, `NODE_PATH` and the C/C++ include path, so `import helper`, `require('helper')` and `#include "helper.h"` find a file saved there; a relative `require('./x')` from `main.js` does not, because `main.js` lives in the run folder. The Files panel is `FilesPanel` (lazy, mounted on first open and then hidden) over `files:list|read|write|create|rename|remove` IPC (`apps/desktop/src/main/files/`): `resolveInside` rejects `..`, absolute paths, drive letters, reserved Windows names and links/junctions that lead out of the workspace, `WorkspaceFiles` does the work, and every call answers `{ok:true,value}` or `{ok:false,message}`. Limits (`FILE_LIMITS`): 2 MB per text file, 10 MB per previewed image, 200 MB of the student's own files checked on save and create (a running program is not limited), 1000 entries per folder. `node_modules`, `site-packages` and dotfolders are hidden unless asked and not counted. Images are shown as `data:` URLs in an `<img>`. Text files open in a separate Monaco model and save by themselves 0.6 s after typing stops. The panel is available only while the exam runs and the teacher's `filesEnabled` is on (`filesRefusal`); files are local only and are not part of the submission.
- Teacher-provided exam files (M15f): the teacher attaches files to a draft or ready exam (`ExamFilesSection`, raw `application/octet-stream` upload with `?name=`). The server keeps the manifest in `exam_files` and the bytes in `<dataDir>/exam-files/<examId>/<fileId>` (`ExamFileService` over `ExamFileRepo` and `ExamFileStore`); names are checked with the shared `checkFileName`, a file with the same name in any letter case replaces the old one, and the limits are `EXAM_FILE_LIMITS` (25 MB per file, 50 MB and 50 files per exam). The manifest travels in `SessionState.examFiles` (empty when the Files switch is off); the bytes never use the WS (512 KB frames) but `GET /api/v1/exam-files/:fileId` over the pinned HTTPS connection with the session token. Student main (`ExamFileSync`, called from the `onExam` hook in `ipc.ts`): while the exam is `hosting` or `running` each file not yet present is downloaded (2 at a time, 3 tries, `downloadExamFile` streams to `<name>.part`, counts and hashes the bytes and renames only if the size and SHA-256 match) into `%LOCALAPPDATA%\ExamGuard\run\<examStudentId>\.examguard\exam-files\<fileId>`. When the exam is `running`, each staged file is copied into the workspace root (`COPYFILE_EXCL`, name checked and resolved with `resolveInside`) and its id is recorded in `revealed.json` next to it, so a file the student deleted is not copied again after a reconnect or restart and a file of that name the student already has is left alone. After that the files are ordinary project files. A failed download is shown in the lobby and the exam screen with Try again.
- Bundle size (2026-10-21, measured on the dev PC): Electron runtime 369 MB; WinLibs MinGW unpacked 947 MB, **535 MB after the C/C++ trim** (measured in M15a); MSYS2 base 225 MB unpacked (locale/man/doc/info dropped at packaging, M45); npm 12 MB; CPython 59 MB after trimming (144 MB as fetched, M15d). **Measured in M45 (2026-11-03): installer 210 MB, installed 1178 MB** (toolchains 794 MB, app.asar 50 MB). One installer always contains everything.

## 5. Screens: thumbnails and live view
- **Capture** happens in student Electron main with `desktopCapturer` (`types: ['screen']`) for the whole screen. Event screenshots come from the monitor (§3), at a larger size.
- **Thumbnails:** the teacher UI tells the server which students are on the visible page (`thumbs.subscribe`, about 25–30 IDs). The server sends `thumb.start {intervalMs: 4000}` to those students and `thumb.stop` to the rest. A student encodes a 320 px JPEG (`nativeImage.toJPEG`, q≈50, about 10–20 KB) and sends it as a binary frame. The server keeps only the latest frame per student in memory and forwards it to the teacher socket. Budget: 30 × 15 KB / 4 s ≈ 110 KB/s, well under the 1 MB/s target. With 200 on one page it would still be ~750 KB/s. Nothing is stored. Built in M29/M33 (`sockets/thumbRelay.ts`, student `main/thumbs/`, teacher `ThumbnailGrid`): the student streams only while asked and monitoring, the server forwards only frames it asked for, and a page switch is served from the cache at once. Measured with the sim (milestones M29): 30 visible → about 2 % of one core and 113 KB/s; 200 visible → 3.7 % and 754 KB/s.
- **Live view (one student at a time, max 2 open):** teacher clicks → `live.request` → the student creates an `RTCPeerConnection`, adds a `getUserMedia` desktop track (chromeMediaSource, max 1280 px, 8 fps) and sends an offer. Offer, answer and ICE travel as `rtc.signal` through the server. The teacher renderer plays it. Closing it (or 60 s without the panel visible) sends `live.stop`. The deferrable fallback if WebRTC slips is a "fast thumbnail" mode: 960 px every 1 s over WS for the selected student. **The fallback is built (M34, 2026-11-03):** "Live screen" in the student detail sends `thumbs.focus`; the relay switches that student to 960 px every 1 s (`thumb.start` with other values) while the panel is open and the window shown, and the panel closes itself after 60 s hidden. **WebRTC is built (M30/M34, 2026-11-03):** the student app opens one hidden, sandboxed child window per session (`main/live/`, own preload and page, never shown or focused, the only page granted `media`), which captures the primary screen and sends the offer; it is destroyed when the session ends, monitoring ends or the socket closes. The server (`LiveRelay`) only relays signals between the two ends of a session it opened. Chromium's mDNS hiding of host candidates is switched off (`WebRtcHideLocalIpsWithMdns`), since lab networks often do not resolve `.local` names. The teacher's `LiveView` falls back to the fast thumbnail when the peer fails or no video arrives within 10 s.

## 6. Autosave, offline, resume, recovery
- **Answer key:** `(questionId, language)`. Written answers use language `text`. The client keeps a buffer per key and a monotonically increasing `clientSeq` per session.
- **Autosave triggers:** every 10 s if the content changed, plus Run, question switch, language switch and submit. Each save becomes an `answer_versions` row. The server dedupes on `(exam_student_id, client_seq)` and acks the `clientSeq` after the commit. `clientSeq` is one counter per student; after every welcome the client continues past the largest `clientSeq` in `welcome.saved`, so a restarted app never reuses a number. The scheduler is in the renderer (`Autosaver`), main numbers the saves and keeps the unacked ones (`AnswerOutbox`).
- **Offline queue (M17):** every save, event and transcript chunk is also appended to a JSONL file in userData (`queue/<examStudentId>.jsonl`, `main/resume/offlineQueue.ts`). Each line is encrypted with `safeStorage` (DPAPI, user-scoped); an ack appends a `-<key>` line and an empty queue deletes the file. The frames stay in memory too and are re-sent after every welcome until acked; the file only matters after a restart, when `SessionClient.start` loads it. If encryption is unavailable nothing is written (never plaintext). A write that fails is logged and never stops the exam.
- **Reconnect:** WS reconnect with backoff (0.5 s → 5 s, jitter). The token is reused. The server replays the state snapshot (`session.state`). A watchdog drops a socket that has been silent for three ping periods, so a cable pull shows as "reconnecting" within about 15 s.
- **Clock:** the client estimates the server offset from `ping/pong` RTT. Client timestamps (`clientTs`) are in server time. Since M64 student main anchors the server clock on the monotonic clock (`performance.now`): the first sample comes from `welcome.serverTime`, round trips are measured monotonically, the shortest-RTT sample wins but one older than 60 s is replaced, and the offset to the wall clock is recomputed on every pong, so a Windows time change mid-exam is followed within one ping.
- **Deadline:** `deadline = exam.started_at + duration + exam_student.extension_sec + exam.global_extension_sec`, the same for late joiners. "Ending" is not a stored state (M18): between a student's deadline and `deadline + grace` the exam and the student stay `running`/`active`, and the save gate accepts only saves with `clientTs ≤ deadline` that arrive within the grace (`monitoring.graceSec`, default 60 s). A 1 s watcher (`DeadlineWatcher`) then finalizes each working student at their own `deadline + grace`, and ends the exam at `last deadline + grace`; after a restart the first tick does the same for deadlines that passed while the server was down. Finalizing (`SubmissionService`, the same path for the student's Submit, the auto-submit and the teacher's End) flushes the batch writer, takes the newest selected-language version per question (an empty answer for an unanswered question), writes `final_answers`, hashes them into the receipt and sets the student `submitted` (`ended_by_teacher` after a manual End), all in one transaction guarded by the student state, so it happens once. Trusting the client stamp is an accepted risk (see limitations.md). A student whose link is down past their `deadline + grace` (or whose session failed for good) cannot be told by the server, whose listener closes at `ended`: the client applies the same rule (`sessionExit`, with `SessionState.graceSec` and 5 s of slack), releases the window lock and shows the "exam time is over" screen; if the link comes back while the exam is still `running`, the next `welcome` locks it again.
- **Same-PC resume:** `deviceId = SHA-256(HKLM MachineGuid + "examguard")`. Join with the same student ID and the same device while a session exists means the token is re-issued and the session resumes. A different device is rejected and logged (critical `duplicate_login`) until the teacher resets the session. After a restart the app resumes without the PIN: the session file (`session/session.enc`: token, pinned address and fingerprint, names) is loaded in student main, the socket reconnects with the same token, and the renderer asks main to restore the editors (`answers:restore`). Main merges the server's newest version of each buffer (`GET /answers/latest`, asked only when the welcome says versions exist) with the unacked saves from the queue; the higher `clientSeq` wins per buffer and for the selected language. The exam screen waits for this ("Restoring your work…", with Retry) so the student cannot type over work that is safe on the server. The student can also choose **Leave this exam** while the link is down; that removes the session file but keeps the queue. The session file is removed on `unauthorized` (token no longer valid) and when the exam ends.
- **Server crash or restart:** all state is in SQLite (WAL, `synchronous=NORMAL`). On boot the server finds exams in Hosting/Running, restarts listeners with the same cert, port and PIN, recomputes deadlines from stored timestamps (the timer kept running while it was down) and re-advertises mDNS. Students reconnect automatically. Deadlines that passed during downtime are processed with the grace rule once a 60 s reconnect window after the restart is over (M62, `StudentDeadlines.allowLateUntil`): the apps kept working while the server was down, and their queued saves (stamped by the deadline) still count. A failed listener reopen still starts the deadline watcher. Socket handlers, the watcher and the terminal timer catch their own errors, and the process logs any uncaught error instead of exiting.
- **Batching:** events and autosaves are buffered in memory and written in one transaction every 250 ms or every 200 items. Acks are sent after commit.
- **Data folder move (M44, `main/dataFolder/`):** the teacher's data (data-model "Data folder layout") lives in the profile folder unless `<userData>/dataLocation.json` points elsewhere; main reads it through `DataFolder.current()`, so the server, the AI key store and "Show in folder" follow a move without an app restart. Settings → Data folder picks a folder (an empty or missing one is used as it is, otherwise `ExamGuard` inside it; a folder inside the current one or one that already holds data entries is refused) and `DataFolderMover` runs: free-space check → `release-data` to the server, which refuses while an exam is hosting or running or a grading job is unfinished, else closes the database in the same tick (no hosting can start in between) → stop and wait for the process → copy only the data entries (never Electron's own files or `mode.json`) → verify every file by size and SHA-256 → write the pointer and start the server there → once it reports `running`, delete the old entries (any that cannot be deleted are counted, not fatal). Any failure before the switch deletes the partial copy and restarts on the old folder; a server that does not come up from the copy within 30 s switches back too. The restart signs the teacher out, so main also shows the outcome in a message box.
- **Screenshot retention (M44, `services/screenshots/screenshot-retention.ts`):** `retention.screenshotDays` (`null` = keep) deletes pictures with `server_ts` older than N days whose exam is not hosting or running and nulls `events.screenshot_path`, in batches of 500; it runs at every server start before listening and when the teacher saves the setting (`POST /settings/retention/purge`).

## 7. AI grading pipeline (teacher server)
```
GradingProvider { id; gradeAnswer(input: GradingInput, opts): Promise<ProviderResult /* raw text + usage */> }
```
- `apps/server/src/services/grading/`: `providers/gemini.ts` (`@google/genai` pinned 2.30.0, `responseJsonSchema` = `RESPONSE_JSON_SCHEMA` in `prompt.ts`, temperature 0.1, default model `gemini-2.5-flash` until Settings; failures become `ProviderError {kind: rate_limit|server|auth|bad_request|network, retryable}`), `providers/fake.ts` (replays fixtures from `apps/server/fixtures/grading/*.json` by the answer's anon ID, used by all tests; `source: recorded | hand-written`), `prompt.ts` (versioned template, `PROMPT_VERSION`), `validate.ts` (Zod + rules: each `awarded ≤ max`, half-unit steps, criteria names match the guide, total = sum), `pipeline.ts`.
- **Manual smoke test and real fixtures (M37):** `pnpm record-fixture -- <input.json> <name> [model]` grades one answer with real Gemini, key from `EG_GEMINI_API_KEY` in the shell only, and saves `fixtures/grading/<name>.json` (`source: recorded`). Never run by tests.
- **Flow (built M38):** "Evaluate with AI" → one `grading_jobs` row per question (only its `pending` and `needs_manual` answers, so a run from In review grades what is left) → jobs run one after the other in question order; inside a job the answers go through a small worker pool (`pool.ts`, concurrency 4, a Settings value later) → `grade-answer.ts`: retries with exponential backoff (2 s × 2ⁿ) on 429/5xx/network (3×), 2 retries with a repair hint after an invalid reply, then `needs_manual`; a refused key (`auth`) stops the run and fails its jobs. Each attempt stores an `evaluations` row (provider, model, prompt version, raw response or error, the validation problems). `grading-service.ts` owns the queue, Ended → Grading → In review (when nothing is queued or running), cancel (aborts the calls in flight; their answers stay `pending`) and resume. `review-service.ts` serves the review (M39) and writes the teacher's accept/edit (M40) as teacher rows in `evaluations`.
- **Input** has only an anonymous ID (`exam_student.anon_id`), never name or student ID. Built in M37 as `grading/input.ts` (`gradingInput(question, anonId, answer)` copies only the grading fields).
- The API key is decrypted in main and sent to the server over the utilityProcess message port at grading time (`grading-key-request` → `grading-key`, at each start and resume; `provider-source.ts`). It's never written to the DB or logs. Built M43: Settings → AI grading sends the key once over preload to main (`settings:ai-key-set`), which encrypts it with `safeStorage` into `<userData>/secrets.bin` (`main/settings/aiKeyStore.ts`); the renderer only ever gets `{set, source, encryptionAvailable}`. `EG_GEMINI_API_KEY` in the shell is a dev fallback when no key is saved. The model and the pool size come from the `settings` table at each run. Dev: `EG_FAKE_GRADER=1` makes the server grade with `providers/synthetic.ts` (stable hash-based marks, some low confidence, a few 429s and bad replies, no network); the panel shows "Dev fake grader".
- Progress goes out through WS `grading.progress` (the whole `GradingStatus`, throttled to 250 ms per exam). The pipeline is resumable: jobs are rows, so after a restart `resume()` runs every `queued`/`running` job again for its answers still `pending` (graded answers are not sent twice; the retry counts start again).
- **Re-evaluate with an instruction (built M41):** same pipeline plus the teacher instruction in the prompt (the "Teacher's extra instruction" section). Scope: one answer, or all answers on that question except Verified/Modified unless included; only from In review. `reevaluate.ts` creates one `reevaluate` job and marks its answers with `answer_grades.queued_job_id`; they keep their grade until the job grades them (the run takes them from the queue, not from `pending`), so a cancel or a refused key changes nothing and a restart resumes the rest. The new attempts are appended to the history with the instruction; running out of retries still makes the answer `needs_manual`.
- **Finalize and export (built M42):** `services/results/`: finalize needs no `pending`/`needs_manual` answer, takes a backup (`backup.ts`, online SQLite backup + screenshots copy) and then sets `finalized` (+ `finalized_at`, audit `finalize`); review, grading and re-evaluate refuse a finalized exam. The CSV (`results-csv.ts`, from `results.repo.ts`) is built only for a finalized exam and saved to `exports/`; the Results panel shows it in Explorer through main (`exports:reveal`, file name only).
