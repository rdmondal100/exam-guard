# Protocol

Each shape here has a Zod schema in `packages/shared/src/protocol/` with the same name, and the TS type is `z.infer` of it. These shapes are the intent. The schemas are the contract. Marks on the wire are numbers in 0.5 steps (converted to half-units at the DB edge). Times are Unix ms in server time.

## 1. Versioning
- `PROTOCOL_VERSION = { major: 5, minor: 0 }`, exported from `packages/shared`. Major 5 (2026-11-19, M59–M64): the server refuses Submit while paused (`submit.refused paused`; saves are still taken, they hold what was typed before the pause), a `readiness.report` must hold every check exactly once, and the monitor's `monitor_stalled` / `monitor_recovered` events. Major 4 (2026-11-13, M58): pause/resume (`pausedAt` in the session state and hosting info; a 3.x app would keep its editor open while paused) and questions/files added mid-exam. Major 3 (2026-11-12, M52–M57): the teacher and student apps ship as a pair; adds `readiness.report`, `practice` on exams, the join and the session state, and the roster's `readiness` fields. Major 2 (2026-11-12): the monitor moved into the student app (`monitor` replaces `agent` in the join, `monitor.status` replaces `agent.status`, no internet switch, no `agent_lost`), so a 1.x app and a 2.x teacher refuse each other.
- Sent in the mDNS TXT (`v=2.0`), in `POST /api/v1/join`, and in the WS `hello`.
- Different **major** → the server refuses with `426 protocol_mismatch`, and the student app shows "Update ExamGuard to match the teacher's version". Different **minor** is accepted, and unknown optional fields are ignored (schemas are `.passthrough()` only on the receive side of optional blocks).
- URL prefix `/api/v1`. A breaking change bumps major and adds `/api/v2` routes.

## 2. HTTP endpoints

### Student API: `https://<teacher-ip>:47820/api/v1` (only while hosting)
| Method & path | Auth | Body → Response |
|---|---|---|

## 3. WebSocket messages
Envelope for every JSON frame: `{ t: string; id?: string /* for acks */; ...payload }`. Binary frames: `[u8 kind][u16 headerLen][header JSON][payload]`, where kind 1 = thumbnail and kind 2 = screenshot chunk.

### Auth, limits and close codes (built in M12)
- Student `hello` must be the first frame, within 5 s. `ping` or `event` before `hello`, a non-JSON frame or an unknown `t` closes the socket; after `hello` an invalid frame is dropped and logged and the socket stays (M60: closing made the app reconnect and send the same frame forever). A token whose student has not accepted the notice (`not_joined`) is refused with 4401 (M59). Max frame 512 KB. Per socket, `event` and `transcript` are limited to 20/s with a burst of 1000 and `readiness.report` to one per 5 s (burst 5); a frame over the limit is dropped unacked, so the app sends it again after its next welcome (M62). Built so far: `hello`, `ping`, `event` (M15); the rest of the student messages above arrive with their milestones.
- **Monitor events (M22, in-app since 2026-11-12):** the `EVIDENCE_KINDS` of §4 arrive as `event` too. The server stores them with source `monitor`, key `monitor:<examStudentId>:<dedupeKey>` (M59: one student can never block another's key; the app uses `<examStudentId>:<runId>:<n>`, `runId` random per app run) and the classifier's severity (M31, see "Classification and risk" below). A screenshot travels first as binary frames `[0x02][u16 BE headerLen][{ref,index,total}][≤200 KB of JPEG]` and the event names it with `screenshotRef` (= `ref`). The server joins the pieces on the ordered socket, keeps it only if it is a JPEG of at most 2 MB, writes `screenshots/<examId>/<examStudentId>/<eventId>.jpg` and acks the event; missing pieces mean the event is stored without a picture. A binary frame before `hello` closes the socket (4400). `focus_returned` adds its duration to the student's `outsideMs` (once per event).
- **Classification and risk (M31):** every event goes through the server's `EventRecorder`. `classifyEvent` (requirements §8.6): a program on the exam's high-severity list (`exe`, any letter case), a listed site (the `url` host or the `domain` is an entry or under it, so `gemini.google.com` matches only that site) or a private browser window, in focus, in a shot or launched, is high; any other `focus_lost` is low and the time outside raises it (`still_outside` / `title_changed` by the time since the switch on the student's clock, `focus_returned` by `durationMs`: under 10 s low, from 60 s high, medium between); `app_launched` medium; `processes_at_start` medium only with a listed program; `monitor_changed` as in M26; `taskmgr_opened`, `secure_desktop`, `paste_blocked`, `network_lost`, `monitor_stalled` medium; `large_insertion` high; `duplicate_login` critical; the rest low (also the old `app_relaunched` and `agent_lost` of older exams). `riskScore` adds 1/3/8/20 points per low/medium/high/critical event as it is stored, except the neutral types (runs, terminal, packages, `network_restored`, `processes_at_start`).
- **Thumbnails (M29, M33):** the server sends `thumb.start {intervalMs: 4000, width: 320}` to each connected student on any teacher socket's visible page (after the `welcome`, and again after every reconnect) and `thumb.stop` when no page shows them. The student app captures only while it is also monitoring (exam running, student active or locked) and sends binary `[0x01][u16 BE headerLen][{ts}][JPEG ≤256 KB]`; nothing is queued while the link is down. The server drops a frame from a student it did not ask, or one that is not a JPEG, keeps the newest per student in memory (cleared when hosting stops), forwards it as kind 1 with `{examStudentId, ts}` to the teacher sockets watching that student, and sends the cached frames at once on `thumbs.subscribe`. A teacher socket with more than 2 MB unsent skips frames. `thumbs.subscribe` takes at most 200 ids; `[]` or closing the socket stops its streams. **Fast thumbnail (M34 fallback, built 2026-11-03):** a student in any teacher socket's `thumbs.focus` list gets `thumb.start {intervalMs: 1000, width: 960}` instead (focus wins over a grid page) and goes back to the grid values or `thumb.stop` when the focus ends; the frames are the same kind-1 frames, sent to sockets that have the student on their page or in focus.
- **Live view (M30/M34, built 2026-11-03):** `live.open` from a teacher socket → the server refuses with `live.session failed` (`not_connected`, or `too_many` past 2 per socket) or sends `live.session connecting` and `live.request {sessionId, maxWidth: 1280, fps: 8}` to the student. The student app answers with `rtc.signal` (the offer, then its candidates) or `live.state failed` (not monitoring, no screen, capture or peer failure); the teacher answers through the server. `rtc.signal` data is `{type:'offer'|'answer', sdp ≤ 64 KB}` or `{candidate ≤ 1 KB, sdpMid?, sdpMLineIndex?, usernameFragment?}`, and the server relays it only between the two ends of a session it opened (other signals are dropped silently). `live.close`, the teacher socket closing, the student's socket closing or being replaced (a new `welcome`), `live.state` and hosting stop end the session: `live.stop` to the student when its socket is still the same, `live.session ended|failed` with a reason to the teacher. No ICE servers: host candidates only.
- `large_insertion` (M27, app event): `{surface: editor|answer|other, chars, lines, durationMs, preview ≤200, suppressed?}`, at most one per 2 s per student.
- `transcript` (M15b): stored once per `key` (namespaced by student on the server), up to 1 MB per student, then one "truncated" marker; every chunk is answered with `transcript.ack`, also a duplicate or a dropped one. The client re-sends unacked chunks after each `welcome`.
- Terminal switch (M15b): every change (teacher action, Start of a pending window, auto-off at `until`) is pushed to all connected students as `{t:'state', state:{terminal}}`; late joiners get it in `welcome`. The server turns the terminal off itself at `until`.
- `event` (M15): `type` is limited to the app's own types (`APP_EVENT_TYPES`: `run_executed {questionId, language, flags, status, exitCode, timeMs}` (`flags` ≤500 chars since M15c), and from M15b `terminal_opened`, `terminal_closed {reason, exitCode}`, `terminal_command {line, truncated?}` (≤2000 chars), `package_installed {manager: npm|pip|pacman, packages[], line}`); monitor evidence types are in §4. The server stores it with source `app`, the classifier's severity (M31), and dedupe key `app:<examStudentId>:<dedupeKey>` (the client uses the event id). A repeated key is not stored again but is still answered with `event.ack`. The client keeps unacked events in memory and re-sends them after each `welcome`, and in the offline queue (M17); monitor evidence goes there too, without its picture.
- `answer.save` (M16): `clientSeq` is one counter per student (≥ 1), kept across reconnects, and after a welcome the client continues past the largest `saved.clientSeq`. The server keeps each number once (a resend is acked again and changes nothing). `reason` is `interval | run | switch_question | switch_language | submit` (`final` is the server's). `content` ≤ 128 K characters, `flags` ≤ 500. Saves are batched (250 ms or 200 rows) and **`answer.ack` is sent after the commit**. **A save is stored only while** the exam is `running` (also while paused: the app's last save arrives just after the pause begins), the student is `active` or `locked`, `clientTs ≤` the student's deadline, and the server's clock is at most `deadline + graceSec` (the exam's `monitoring.graceSec`, M18), or within the reconnect window after a server restart (M62, 60 s). A save for an unknown question or a language the question does not allow (written and language-less code questions use `text`) is dropped as well. Every dropped save is acked, so the client stops re-sending it. "Selected" for a question = the language of its newest version saved with `selected: true`.
- `submit` (M18): the student presses Submit, or the client re-sends the frame after each `welcome` until it gets an answer (after the unacked saves, on the same ordered socket). The server writes the batch of saves it already holds, makes the answers final (`final_answers`, state `submitted`) and answers `submit.result` with the receipt; a repeat gets the same receipt. `submit.refused` says why not (`not_running`: the exam is not running; `not_working`: the student is not `active`/`locked` and has no receipt; `paused` (M60): the exam is paused, and the app keeps the Submit and sends it again when a `state` push ends the pause). A final close (4401, 4409, 4426) or a fingerprint mismatch settles a pending Submit as failed in the app. The server also pushes `{t:'state', state:{studentState, receipt}}` to the student whenever the answers become final without a `submit` (auto-submit at deadline + grace, or the teacher ending the exam: `studentState` is then `ended_by_teacher`). Receipt: `hash` = SHA-256 of the canonical JSON of `answers` sorted by `questionId`, each `{questionId, language, sha256}`; `sha256` = SHA-256 of the UTF-8 content (`packages/shared/src/protocol/submission.ts`).
- Student close codes: `4400` bad or missing hello, `4401` unknown token or wrong exam, `4426` protocol major mismatch, `4409` replaced by a newer socket of the same student, `4503` not hosting (hosting stopped). The student client does not retry after 4401, 4426 or 4409; it retries everything else with backoff.
- `welcome.state` (M13): `examState` is the real exam state. While `hosting`: `deadline` null, no `questions`. While `running`: `deadline` is the shared end time, `questions` is the `QuestionForStudent` list, and a student still in `lobby` (late joiner) becomes `active`. `saved` is the newest stored version of each buffer (M16: `clientSeq` and whether it is the selected language); `monitoring` is false until its milestone. `graceSec` (optional, the exam's monitoring grace) lets the client tell when the server has finalized it while the link is down. `runLimits` (M43, optional; defaults when absent) are the exam's code-run limits, fixed at hosting start.
- **Added mid-exam (M58):** `POST /exams/:id/questions` also works while `hosting` or `running`: the question must be complete (`questionProblems`: sample answer and criteria unless practice, a language for code) or 422 `question_incomplete` `{problems}`; it goes last, and while running every working student gets `state {questions}` (the whole list; logged `add_question`). Changing, deleting or reordering stays 409 `invalid_state`. `POST /exams/:id/files` likewise takes a new name while hosting or running (a taken name → 409 `file_exists`; delete → 409); with the Files panel on, every connected student gets `state {examFiles}` and the app downloads it (into the project folder if running); logged `add_file {name}`.
- On `POST /start` the server sends every connected student `{t:'state', state}` with the same fields (full state for now). Students not connected get the same data in their next `welcome`.
- Teacher WS takes the token as `?token=` (a browser WebSocket cannot set headers). A wrong token or a teacher who is not logged in gets the socket closed with `4401` right after the upgrade; a logout closes every open teacher socket with `4401` too (M59). `subscribe` replaces the previous subscription.

### Flow rules
- The server pushes events and state through a per-student `serverSeq`. `hello.resume.lastServerSeq` lets the server resend missed commands (messages, lock). Built instead (M35): a lock is part of the `welcome` state, and unacked teacher messages are re-sent after every `welcome` (kept in server memory, at most 20 per student). A reset session closes the student's socket with 4401, so the old PC stops retrying.
- The student sends `answer.save` and `event` only after `welcome`. Queued items are flushed in `clientSeq` order.
- The server drops a student WS with no frame for 15 s and marks them `connected=false`. A student who stays disconnected for 10 s while the exam is `running` gets a server `network_lost` event (`details.since` = when the socket closed); the next connection gets `network_restored` (`details.since`, `details.downMs`). Whether an outage is open is read from the `events` table, so a server restart in the middle of one still ends it. Hosting stop and the end of the exam raise nothing. (M17)
- The client also drops a socket that has received nothing for 3 ping periods (15 s) and reconnects, so a pulled cable is noticed without waiting for TCP. (M17)
- `hello.resume.lastServerSeq` is sent as 0: the server has no per-student `serverSeq` commands yet (lock and messages, later milestones).

## 4. Monitor evidence (in the student app)
The named pipe to the Rust agent (`\\.\pipe\examguard-agent`, `PIPE_VERSION`, `hello`/`heartbeat`/`net.set`/`evidence`) was removed on 2026-11-12: student main monitors by itself (architecture §3) and sends what it sees straight as WS `event`s. Schemas: `packages/shared/src/protocol/monitoring.ts`.
```ts
type EvidenceKind = 'focus_lost'|'focus_returned'|'title_changed'|'still_outside'|
                    'app_launched'|'processes_at_start'|'monitor_changed'|'secure_desktop'|'taskmgr_opened'|
                    'monitor_stalled'|'monitor_recovered';   // M63: the monitor's own health (durationMs)
type EvidenceDetails = { exe?:string /* ≤260 */; path?:string; pid?:number; title?:string /* ≤500 */;
                         domain?:string; url?:string /* ≤2048 */; privateWindow?:boolean;   // Chrome/Edge in front
                         durationMs?:number;                                                // focus_returned
                         processes?:{exe:string;pid:number}[] /* ≤300, processes_at_start */;
                         monitors?:number; monitorsBefore?:number;                          // monitor_changed
                         desktop?:'lock'|'secure' };                                        // secure_desktop
type MonitorPolicy = { screenshotOnSwitch:boolean; titleChangeShots:boolean; periodicOutsideSec:number /* 0 = off */;
                       minShotGapSec:number; maxWidth:number; jpegQuality:number };         // from SessionState.monitoringPolicy
```
- `focus_lost` for each new outside window, `title_changed` for a new title or site in it, `still_outside` every `periodicOutsideSec`, `focus_returned` with the whole stretch outside; a shot at the switch, a title change and the periodic one, never twice within `minShotGapSec` (an event whose shot the gap holds back is still sent).
- `processes_at_start` once at the start (programs with a window); `app_launched {exe, path, pid}` for a process whose first window appeared (`taskmgr.exe` → `taskmgr_opened`); no screenshot.
- `monitor_changed {monitors}` for more than one screen at the start, `{monitors, monitorsBefore}` on a change; `secure_desktop {desktop:'lock'}` for the lock screen and `{desktop:'secure'}` when no window could be read for 2 s. Roster `RosterEntry.monitors` = the count of the student's last `monitor.status`.
- **Paste guard (M25).** App event `paste_blocked {surface: 'editor'|'answer'|'terminal'|'other', chars, lines, preview /* ≤200 chars */, suppressed?}`, at most one per 2 s (`suppressed` = the blocks folded into it); server severity `medium`, source `app`. Renderer → main IPC `clipboard:paste-blocked` with the same body (`PasteBlockedReportSchema`).
- **Teacher events list (M25).** `GET /exams/:id/events?view=monitoring` returns the monitor's evidence (`source='monitor'`) plus the app and server events in `MONITORING_EVENT_TYPES`; the teacher's Events panel uses it instead of `source=monitor`. `source`, `severity`, `studentId`, `after` and `limit` still work alongside.

### Removed (2026-11-12)
- The internet switch (M21b): `SessionState.internet`, `HostingInfo.internet`, the `internet` exam action, `internet.status`, `RosterEntry.internetBlocked` and the `internet_*` app events. Old audit rows still show as "Allowed/Blocked the internet".
- The tamper lock (M24): the `agent_lost` app event and `lockReason:'agent'` (migration 0016 makes such locks `teacher`).
- Severity is never decided on the student PC. The server classifies `kind` + `exe`/`title`/`domain`/`url` against the exam's monitoring settings.
